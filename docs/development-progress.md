## 이번 단계의 경계

- KB `SSQM2932`의 `tl_data_cnt`를 Flutter에서 숫자로 해석할 수 있을 때 현재 표시 잔고 항목 수와 비교해 차이를 경고합니다. 값이 없거나 해석할 수 없으면 미제공으로 남깁니다. 일치도 전체 조회 완료의 증거가 아니며, 차이 역시 원인 확인이 필요합니다. 자동 재조회·AI 판단·주문 상태는 바꾸지 않습니다.
- KB `SSQM2932` 결제기준 잔고 응답의 `valuationWeightRate`를 누락 시 `null`로 유지하고 Flutter의 읽기 전용 상세 화면에 현재 응답 항목을 표시합니다. `SSQM1801` 보유주식 조회의 계산 비중은 별도 모드로 분리하며, 평가금액이 없으면 산정 불가로 표시합니다. 실제 계좌 앱과의 대조는 아직 하지 않았고 AI 추천·주문 조건에는 연결하지 않았습니다.
- Windows 알림 대기 API에 사용자 범위의 배타적 `afterAlertId` 커서를 추가했습니다. 앱은 최대 5페이지씩 처리하고 다음 주기에 이어받으며, 끝에 도달하면 앞의 실패 건을 다시 확인합니다. 한 건의 표시·완료 기록 실패가 뒤의 알림을 막지 않습니다.
- 표시 성공 뒤 `/sent` 기록 실패는 Windows 로컬 `alert-display.log`에 알림 ID만 기록하여 재시작 후에도 표시 없이 확인만 재시도합니다. 서버 확인이 성공하면 완료 이벤트를 기록합니다. 표시 직후 로컬 기록 전 종료, 파일 쓰기 실패, 저장소 손상 등에서는 중복 표시 가능성이 남으므로 정확히 한 번 전달은 주장하지 않습니다. 실기기 장기 운영 검증은 아직 하지 않았습니다.
- Flutter 알림 탭에서 마지막 점검 시각, 이번 점검의 건별 실패 수, 로컬 전달 기록 확인 대기 수, 전체 점검 실패 여부를 확인할 수 있습니다. 완전한 대기 목록 조회가 끝나고 서버에 더 이상 없는 로컬 확인 기록만 정리합니다. 이 표시는 최근 앱 실행 중 상태이며 장기 운영 검증의 대체물이 아닙니다.
- 보유 종목 분석 요청에 등록된 활성 보유 종목의 **매입 원금 기준** 동일 종목 비중과 설정 자본금 대비 비중을 추가합니다. 동일 시장·종목코드의 보유 건을 합산하며, 자본금 미설정 또는 종목 기록 누락 시 임의 수치를 만들지 않습니다. 이는 KB 실계좌의 실시간 평가 비중이 아닙니다.
- Python 분석기는 권장 자본금 한도를 넘은 종목의 신규 매수 신호만 보류하고 손절·익절 판단을 우선합니다. 관심 종목에는 비중 신호를 적용하지 않습니다. 실주문 전송에는 영향을 주지 않습니다.
- 보유 종목의 AI·규칙 fallback 분석은 실제 시세 Provider에서 양수 현재가를 받은 경우에만 실행합니다. 시세가 없을 때 화면 조회용 매입가 fallback을 분석 현재가·수익률로 사용하지 않고, 새 추천·알림을 만들지 않습니다. 화면·포트폴리오 평가용 fallback 정책은 변경하지 않았습니다.
- 보유 종목 AI 응답의 상태·추천 유형, 실제 손절·익절 임계값, 등록 자본금 대비 매입 원금 비중 한도를 다시 확인합니다. 모순된 응답은 저장하지 않고 검증된 현재가를 사용하는 규칙 분석으로 대체합니다. AI 서버의 분석 정확도 자체나 실계좌 수익성을 검증했다는 뜻은 아닙니다.
- 관심 종목 ID를 사용자 소유권으로 확인하고 실제 시세가 있을 때만 Python `WATCHLIST` 분석을 실행합니다. 가짜 매수가·손익률·손절·익절 기준은 만들지 않으며, AI 서버 장애 시에는 중립 `HOLD`로 저장합니다. 추천 이력에는 출처가 남고, 대시보드 대표 추천은 보유 종목 결과만 선택합니다. 모의·실주문 전송과는 무관합니다.
- KB `SSQM2341` 조회 API는 지정일의 체결·미체결 항목, 다음키, 주문번호별 최대 10페이지 대조 결과를 반환합니다. 전체 페이지 확인 여부는 `completeScan`으로 표시합니다.
- 수량으로 명확히 구분되는 `OPEN`·`PARTIAL`·`FILLED`만 표시하고, 거절 사유·취소 가능성·수량 불일치 또는 불완전한 페이지 조회는 `UNKNOWN`/`completeScan=false`로 남깁니다.
- 수동 승인 확인 시 승인 ID를 기본키로 한 `READY` 제출 가드를 같은 트랜잭션으로 저장합니다. 기존 승인 건은 `LEGACY_REVIEW`로 이관해 예약을 막습니다. 내부의 원자적 예약은 한 번만 성공하고, 예약 뒤 불명확하면 `UNCERTAIN`으로 남겨 재시도를 막습니다. `GET /api/v1/orders/approvals/{approvalId}/submission`으로 상태를 확인할 수 있습니다.
- 새 가드에는 승인 확인 후 90초의 예약 기한을 저장하고, DB 갱신 조건에서 만료를 차단합니다. 기한이 지난 `READY`는 조회 시 `EXPIRED`로 표시하며, 기존 기한 없는 `READY`는 `011` 마이그레이션에서 `LEGACY_REVIEW`로 바꿉니다.
- 새 승인은 KB 계좌·상품코드·인증값·엔드포인트의 HMAC 지문에 묶입니다. 승인 확인과 내부 예약에서 계좌 설정 변경을 차단하고, 상태 조회는 유효 기한 안의 변경을 `ACCOUNT_CHANGED`로 표시합니다. 기존 지문 없는 `READY`는 `012` 마이그레이션에서 `LEGACY_REVIEW`로 바꿉니다. 계좌번호 원문은 승인 DB에 저장하지 않습니다.
- `RESERVED`·`UNCERTAIN` 승인에 대해 알려진 주문번호로 KB 이력을 최대 10페이지 조회하고, 승인 당시 주문안과 조회 행을 함께 반환합니다. 조회 요약은 감사 기록으로 보존하지만 접수·체결을 자동 확정하거나 가드를 해제하지 않습니다.
- 주문번호를 모르면 날짜별로 최대 10페이지·200행을 조회해 승인 당시 주문안과 함께 보여줍니다. 페이지·행 수 한도나 반복 커서는 `completeScan=false`로 남기고 조회 요약만 저장합니다. 행의 유사성이나 빈 결과를 주문 성공·미접수 판단에 사용하지 않습니다.
- 별도 기본 OFF 실주문 스위치와 운영 IP/MAC 형식 점검을 추가하고, 민감값 없이 차단 이유를 API·Flutter 설정 화면에 표시합니다. 전송 어댑터 미연결 검사는 항상 실패하므로 모든 설정을 채워도 `canSubmit=false`입니다.
- 설정 화면에서 수동으로 KB `SSQM2341` 첫 페이지의 읽기 전용 조회 상태를 점검할 수 있습니다. 설정 누락 시 호출하지 않고, 결과는 `VERIFIED`·`CONFIGURATION_BLOCKED`·`UNVERIFIED`로만 표시합니다. 테스트는 모의 응답으로 통과했으며 실계좌의 조회 권한·응답은 아직 확인하지 않았습니다. 조회 성공도 주문 제출 권한을 뜻하지 않습니다.
- 수동 점검의 민감정보 없는 마지막 결과를 사용자별로 저장하고 설정 화면 재진입 시 조회합니다. 마지막 결과 조회는 KB를 다시 호출하지 않으며, 과거 기록을 현재 권한이나 주문 가능 판정에 사용하지 않습니다. 기존 DB에는 `014_order_read_only_probe_checks.sql` 적용이 필요합니다.
- 저장된 수동 점검을 사용자별 최근 10건까지 조회하고 설정 화면에서 요청할 때만 펼쳐 봅니다. 시간순 상태 변화 확인용이며 주문 행·민감값 없이 표시하고, 이력 조회는 KB 재호출·주문 가능 판정에 관여하지 않습니다.
- 점검 기록 저장소 접근 실패를 `PROBE_STORAGE_UNAVAILABLE`(503)으로 구분하고, 수동 점검에서는 KB 호출 전에 테이블 접근을 확인합니다. Flutter에는 안전한 DB 마이그레이션·연결 안내만 표시합니다. 이 수정은 실계좌 권한 확인이나 실주문 준비율을 높인 것으로 계산하지 않아 10단계 71%, 전체 약 87.0%를 유지합니다.
- 2026-10-02 Windows에서 Ubuntu 백엔드 `/health`는 200, 주문 준비 상태의 `ACCOUNT_NUMBER`는 실패, `/orders/readiness/probe/latest`는 기존 배포 코드에서 `INTERNAL_ERROR`(500)를 반환했습니다. `014` 누락 또는 DB 장애는 운영 로그·DB 확인 전까지 원인 미확정입니다. 민감한 계좌 설정값은 확인하거나 기록하지 않았고 실제 KB 점검 POST는 실행하지 않았습니다.
- Ubuntu 배포를 위한 읽기 전용 `scripts/check-kb-probe.ps1`을 추가하고 기존 볼륨의 `014` 테이블 확인·백업 후 적용 절차를 문서화했습니다. 현 배포 API에서 health/readiness는 200, `ACCOUNT_NUMBER`는 실패, 점검 최신/이력 조회는 모두 `INTERNAL_ERROR`(500)였습니다. 서버 DB·로그는 SSH 세션 접근이 없어 아직 직접 확인하지 못했으므로 원인은 미확정입니다. 이 운영 진단 보강은 기능 구현 점수에 반영하지 않아 10단계 71%, 전체 약 87.0%를 유지합니다.
- Ubuntu 터미널에서 실제 배포는 `.env.prod`가 아닌 `.env.dev` 기반 `sagopalgo-*-dev` 컨테이너임을 확인했습니다. 사용자가 실행 중인 MySQL 컨테이너의 테이블 목록에서 `order_read_only_probe_checks`가 없음을 확인했습니다. 새 백엔드 재실행 후 GET 최신/이력 조회는 모두 `PROBE_STORAGE_UNAVAILABLE`(503)으로 바뀌어 테이블 부재와 일치합니다. 아직 백업·`014` 적용·적용 후 재검증은 완료되지 않았고, KB 점검 POST는 실행하지 않았습니다. 기능 점수는 변경하지 않습니다.
- 개인용 서버 설정을 루트 `.env.example`·`.env`와 단일 `docker-compose.yml`로 통합했습니다. MySQL 볼륨은 이름을 명시한 기존 볼륨만 연결하고, 직접 관리 포트는 Docker 호스트의 루프백에만 열며 Nginx는 지정 IP만 허용합니다. Windows 앱 `.env`는 비밀값 분리를 위해 그대로 유지합니다. Ubuntu의 실제 설정·볼륨 전환, DB 백업과 `014` 적용은 아직 실행하지 않았으며 이 구성 정리는 10단계 71%, 전체 약 87.0%의 기능 점수에 반영하지 않습니다.
- 주문 전송·자동 재시도·정정·취소 API는 추가하지 않았습니다. 가드 예약은 아직 전송 어댑터에 연결되지 않았습니다. 실계좌의 주문 이력 응답 검증은 별도 수동 확인이 필요합니다.

## 다음 우선순위

1. 저장된 수동 점검 이력을 바탕으로 실계좌의 읽기 전용 응답·권한을 확인하고 운영 IP/MAC 요구사항을 별도로 검증한 뒤, 가드 예약을 향후 전송 어댑터에 연결하며 사용자 재확인·실패 감사 로그를 완성합니다. 네트워크 오류 직후 자동 재전송은 금지합니다.
