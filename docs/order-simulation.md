# 주문 시뮬레이션: 확인 순서와 배포

기존 `모의` 탭의 AI 신호 가상 매매에 **주문 시뮬레이션 작업 화면**을 추가했습니다. 실제 KB 모의투자 서버가 아니라 앱 서버 내부의 가상 증권사입니다. 실계좌 인증값·시세·현금·보유분과 기존 `PAPER` 거래 원장을 사용하지 않습니다.

## 진입과 가상 계좌

`모의` 탭 → `주문 시뮬레이션 · 실패/체결 시나리오 시험`을 엽니다. 기존 AI 모의매매가 자본금 미설정으로 막혀 있어도 진입할 수 있습니다. `새 가상 세션`의 시작 현금을 입력합니다. 기본 입력은 1,000만원이며 실제 앱 자본금과 관계없습니다. 시작 현금은 0원 초과~10억원 이하입니다.

- 새 세션은 보유 0주, 가정 시세 `KOSPI:005930 = 75,000원`으로 시작합니다. 이 가격은 테스트용 고정값이며 현재가가 아닙니다.
- 다른 종목 또는 가격은 종목코드·시장·가격을 입력하고 `입력 가격을 가정 시세로 저장`으로 설정합니다. 이후 주문 가격만 바꿔 이탈률 차단도 시험할 수 있습니다. 자동으로 실제 시세를 조회하지 않습니다.
- 국내 6자리 코드, 정수 지정가·정수 주식 수량, 1회 100만원, 가정 시세 대비 5% 이내를 사용합니다. 이 값은 시뮬레이터의 고정 시험 설정이며 실주문 서버의 운영 설정을 읽거나 변경하지 않습니다.
- 가상 현금·보유 주식에서 미체결 주문 예약분을 차감해 신규 주문을 검사합니다. 새 세션은 기존 세션 기록을 초기화하지 않습니다. 최근 20개 세션을 선택해 다시 볼 수 있으며 세션당 명령 100건·이벤트 1,000건으로 제한합니다.

## 주문 승인과 전송

1. 종목·방향·지정가·수량과 시나리오를 선택합니다. 기본 수량 2주로 부분체결도 시험할 수 있습니다.
2. `모의 주문 검증·승인` → 검증된 주문안 확인 → `모의 승인 기록 저장`을 선택합니다. 90초 토큰은 해시로 보관하고 한 번만 소비합니다.
3. 별도 최종 확인 창에서 가상 계좌임을 체크하고 `모의 주문 전송`을 선택합니다. 이 확인 문구와 API는 실제 주문 경로와 다릅니다.
4. `PREPARED → READY → SENDING → ACCEPTED/REJECTED/UNKNOWN`과 모의 전송 횟수, 가상 증권사 상태·체결량을 확인합니다. 제출 전 예약을 커밋하고, 같은 명령을 다시 요청해도 추가 전송하지 않습니다.
5. 미사용 PREPARED/READY는 90초 후 만료됩니다. 만료·새 화면 진입으로 토큰을 다시 발급하거나 기존 승인을 전송하지 않습니다. 필요하면 새 주문안을 준비합니다.

실주문과 **공통 코드**로 지정가/정정/취소 요청 인코딩·응답 분류, 승인 토큰 발급/해시/기한, 이탈률·자원 비교, 원주문 변경 조건과 `예약 커밋 → 단일 전송 → 결과 저장` 순서를 처리합니다. 환경별 계좌 조회·인증·저장 어댑터는 분리합니다. 시뮬레이터에는 KB HTTP 클라이언트나 실주문 설정을 주입하지 않습니다. 이 테스트가 KB 계좌 권한·IP/MAC·운영 응답·실제 체결을 검증하는 것은 아닙니다.

## 시나리오

| 선택 | 클라이언트 결과 | 가상 증권사·계좌 상태 |
|---|---|---|
| 미체결 대기 | ACCEPTED | OPEN, 주문금액/주식 예약. `1주 가상 체결` 또는 `잔량 가상 체결`로 진행 |
| 부분체결 | ACCEPTED | 신규/정정 수량의 절반을 정수 내림 체결. 2주 이상 필요, 잔량 예약 유지 |
| 전량 체결 | ACCEPTED | 신규/정정 전량을 지정가로 즉시 가상 체결 |
| 명시적 거절 | REJECTED | 접수·체결·자원 예약 없음 |
| 접수 전 응답 유실 | UNKNOWN | 증권사 주문 없음. 가상 현금은 유지하지만 신규 전송 차단 |
| 접수 후 응답 유실 | UNKNOWN | 신규/정정은 전량 체결, 취소는 취소 처리. 클라이언트 결과는 미확정으로 유지 |
| 전송 예약 직후 중단 | SENDING/RESERVED | 전송 0회. 잠금 유지·복구 불가 |
| 접수 후 반환 기록 실패 | SENDING/DISPATCHING | 전송 1회·증권사 접수. 종료 근거 없음·복구 불가 |
| 접수 후 결과 저장 실패 | SENDING/RETURNED | 증권사 접수 상태를 저장한 뒤 결과 저장 단계에서 의도적 오류. 반환 결과 RETURNED 별도 보존. 명시적 기록 복구 가능 |

응답 유실은 실제 네트워크 장애를 일으키지 않고 예외로 재현합니다. 저장 실패도 운영 DB를 손상시키지 않고 결과 저장 단계에서 의도적 오류를 반환합니다. 가상 증권사의 상태는 시험을 위한 정답 데이터로 별도 보여줍니다. 실주문에서 응답을 잃었는데도 같은 정보가 제공된다는 뜻이 아닙니다.

`SENDING/UNKNOWN`이 있는 세션은 새 전송을 막습니다. 새로고침은 GET만 수행합니다. 화면 재진입·서비스 객체 재생성 후에도 DB의 동일 상태와 전송 횟수가 유지됩니다. 다른 시나리오는 새 세션에서 실행합니다. 후속 019에서는 RETURNED 결과가 남은 SENDING만 명시적으로 복구합니다. UNKNOWN, RESERVED, DISPATCHING 및 기존 증거 없는 SENDING은 차단을 유지합니다. [복구 화면·배포 절차](order-dispatch-recovery.md)를 참고합니다.

## 체결·정정·취소 확인 예시

1,000만원 세션에서 기본 가정 시세 75,000원·2주를 사용합니다.

1. **대기/체결:** 미체결 대기 매수 접수 → 현금 1,000만원, 사용 가능 985만원. 1주 체결 → 현금 992만5천원, 사용 가능 985만원, 보유 1주. 잔량 체결 → 현금/사용 가능 985만원, 보유 2주.
2. **매도:** 보유 2주를 전량 체결 매도 → 현금 1,000만원, 보유 0주. 보유가 없거나 다른 미체결 매도에 예약된 주식은 중복 매도할 수 없습니다.
3. **정정:** 새 세션에서 미체결 대기 매수 접수 → `지정가 인하 검토` → 74,000원·대기 시나리오로 승인/최종 확인. 기존 주문은 REPLACED, 새 주문은 OPEN이며 사용 가능 금액은 985만2천원입니다.
4. **취소:** 새 세션의 전량 미체결 신규 주문에서 시나리오를 `미체결 대기`로 선택하고 `전부 취소 검토`를 진행합니다. 취소 후 예약이 해제되고 가상 현금·보유 수량은 변하지 않습니다. 취소에는 부분/전량 체결 시나리오를 지정하지 않습니다.
5. **제한 확인:** 실주문과 같이 당일 전량 미체결 신규 주문에 한 차례 지정가 인하/전부 취소만 허용합니다. 부분체결 뒤 변경, 가격 증액, 같은 원주문 재변경은 차단되어야 합니다. 체결 후에는 잔량을 초과하거나 소수 주식 수량으로 체결할 수 없습니다.
6. **중복/재시작:** 최종 확인 뒤 처리 중 버튼과 닫기가 잠기며, 같은 명령의 모의 전송 횟수는 1회를 넘지 않아야 합니다. SENDING/UNKNOWN 세션을 다시 열어 상태와 신규 전송 차단이 유지되는지 확인합니다.

체결은 사용자가 고른 시나리오/수동 단계에서 지정가로 처리합니다. 실제 호가·체결 우선순위·유동성·장 운영 시간·수수료·세금·슬리피지를 모델링하지 않습니다. 이 화면으로 체결 가능성이나 전략 수익성을 판단하지 않습니다.

## DB와 배포

PR 병합 후 최신 develop을 가져오고 기존 DB를 백업한 뒤 018을 적용합니다. 017 운영 적용 여부는 별도로 확인해야 하며 018이 앞선 마이그레이션을 대체하지 않습니다. 실주문 스위치는 OFF로 유지합니다.

```bash
set -e
git switch develop
git pull --ff-only origin develop
backup="sagopalgo-before-018-$(date +%Y%m%d-%H%M%S).sql"
docker compose --env-file .env exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump -uroot --single-transaction --routines --triggers "$MYSQL_DATABASE"' > "$backup"
test -s "$backup"
docker compose --env-file .env exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "$MYSQL_DATABASE"' < Back/database/migrations/018_order_simulation_sessions.sql
docker compose --env-file .env exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "$MYSQL_DATABASE" -e "SHOW CREATE TABLE order_simulation_sessions;"'
docker compose --env-file .env up -d --build --no-deps spring-api
```

새 EXE는 기존 `Front/app_version/build/windows/x64/runner/Release/SagoPalgo.exe` 경로입니다. 018 저장소가 없으면 `SIMULATION_STORAGE_UNAVAILABLE`(503)과 적용 안내를 표시합니다. 실주문·기존 PAPER API는 018 테이블을 참조하지 않습니다. 에이전트가 운영 DB나 실제 주문 스위치를 변경하지 않았습니다.

## API와 저장 분리

모든 경로는 `/api/v1/orders/simulations` 아래이며 현재 사용자 소유 세션만 읽거나 변경합니다. 실제 주문의 숫자 승인 ID와 별도 UUID·별도 테이블을 사용하고 LIVE/PAPER 거래 기록·실제 제출 가드에는 쓰지 않습니다.

| 메서드/경로 | 동작 |
|---|---|
| GET, POST 기본 경로 | 최근 20세션 조회 / `{cash}`로 가상 세션 생성 |
| GET `/{sessionId}` | 저장 계좌·명령·가상 증권사 상태·이벤트 조회 |
| POST `/{sessionId}/quotes` | `{stockCode,market,price}` 가정 시세 설정 |
| POST `/{sessionId}/commands/prepare` | `{plan,kind,parentId,scenario}` 검증 및 승인 준비 |
| POST `/{sessionId}/commands/{id}/confirm` | `{token,acknowledged:true}` 승인 기록 |
| POST `/{sessionId}/commands/{id}/submit` | `{acknowledged:true,confirmation:"모의 주문 전송"}` 모의 단일 전송 |
| POST `/{sessionId}/commands/{id}/recover` | `{acknowledged:true,confirmation:"저장된 전송 결과 복구"}` 저장 결과만 반영. 추가 전송 없음 |
| POST `/{sessionId}/orders/{orderNo}/fill` | `{quantity}` 남은 가상 주문의 수동 체결 단계 |

세션 JSON은 내부 토큰 해시를 보관하지만 API 상태에는 해시를 반환하지 않습니다. 세션 행 잠금·revision 검증과 독립 트랜잭션으로 동시 승인·제출·체결을 직렬화합니다. 진짜 계좌처럼 보이는 가짜 API 키를 만들거나 실제 인증 경로를 우회하지 않습니다.

## 자동 검증 범위

격리 MySQL 8.4에서 018 적용/재적용, JSON 상태 매핑, 현금/주식 예약과 매수·매도, 동시 같은 명령/다른 명령 제출, 9개 응답/중단 시나리오, 만료·시세 변경·자원 부족 차단, 정정/취소·부분체결 제한, 서비스 객체 재생성 후 기록 유지 및 실제 주문/PAPER 원장 무변경을 검증합니다. 기존 016·017 통합 테스트도 함께 실행합니다.

019 후속 포함 백엔드 전체 326건(실제 MySQL 통합 40건), Flutter 전체 155건 통과, Dart 분석 이슈 없음 및 Windows Release 빌드 성공을 확인했습니다. 테스트용 컨테이너·네트워크는 검증 후 정리했습니다.

재현은 [격리 MySQL 테스트 실행 절차](kb-manual-orders.md#격리-mysql-통합-검증-재현)를 따릅니다. 이 작업에서 실제 KB 주문·장애 유발·실제 계좌 대조는 수행하지 않습니다. RETURNED가 없는 SENDING과 UNKNOWN 부분체결/변경 주문 대조 및 11번 자동매매는 후속 범위입니다.

019 후속 변경은 [SENDING 기록 복구](order-dispatch-recovery.md)에 정리했습니다. SAVE_FAILURE의 반환 결과를 적용해도 모의 전송 횟수·가상 증권사·현금·보유분은 변하지 않습니다. 이전 JSON 세션의 필드가 없으면 LEGACY_UNVERIFIED로 조회하며 복구를 열지 않습니다. 내부 실행 UUID와 토큰 해시는 API에서 제외합니다.
