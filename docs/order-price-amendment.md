# 지정가 변경: 인하와 제한적 증액

기준일: 2026-11-01. 당일 앱에서 접수한 전량 미체결 신규 주문의 한 차례 가격 변경을 인하에서 증액까지 확장했습니다. 일부 수량 변경·부분체결 뒤 변경·추가 정정은 포함하지 않습니다. 실제 주문을 실행하거나 운영 설정/DB를 변경하지 않았습니다.

후속에서 **시뮬레이터만** 추가 정정·일부 수량 변경과 예약금 재사용을 지원합니다. 아래 전체 금액·한 차례 제한은 실제 KB 정책으로 유지하며, 가상 화면/수치 예시는 [새 가상 수량·예약 정책](order-partial-changes.md)을 우선합니다. 실제 KB 4·5번 적용은 미완료입니다.

## 공식 계약과 지원 범위

[KB 공식 SSAM1805 정의](https://openapi.kbsec.com/api/apis/catalog/28577def-666f-4d77-b9dc-5904db58ba49/tr-list)의 요청은 원주문번호, 주문단가 9자리, 주문수량 10자리, 전부 정정 `crct_clsf=2`, 정규장 `mkt_tm_clsf=1`, 지정가 `ordr_ccd=00`, KRX `sor_ordr_ccd=K`를 사용합니다. 기존 요청 형식을 그대로 사용하고 새 지정가만 승인안에 저장합니다. 조회 응답의 정정·취소 완료 코드값을 추가로 추정하지 않습니다.

공개 정의만으로 증액 시 기존 예약금/증거금 반환 시점과 재사용 범위를 확정할 수 없습니다. 따라서 기존 예약금을 더하거나 증액 차액만 검사하지 않고, 아래의 보수적인 앱 정책을 적용합니다. 실제 KB의 접수/체결 성공을 검증했다는 뜻은 아닙니다.

| 변경 | 자원 조건 |
|---|---|
| 매수 지정가 인하 | 기존과 동일 수량으로 예약금이 증가하지 않으므로 신규 현금 중복 검사는 제외. 실제 시세·이탈률·전체 주문금액 한도·계좌/주문 스위치는 검사 |
| 매수 지정가 증액 | 위 조건에 더해 현재 주문가능현금이 **새 지정가 × 기존 전체 수량** 이상이고 BUYING_POWER 검사가 명시적으로 성공해야 함. 누락/조회 실패도 거절 |
| 매도 지정가 인하/증액 | 기존 예약 주식의 동일 수량을 유지. 신규 매도가능수량 중복 검사와 매수 현금 검사는 제외하고 기존 시세/한도 조건 검사 |

가격이 같거나 0 이하·소수 원화·필드 범위 초과이면 거절합니다. 시세 이탈률·1회 주문금액 한도는 증액된 **전체 금액** 기준입니다. 준비 때와 전송 직전에 전량 미체결·자원·시세·한도를 다시 확인합니다. 준비 중 계좌가 바뀌면 자식 승인도 저장하지 않습니다. 기존 원주문 가드·90초 토큰·단일 전송·별도 실제 전송 동의는 유지합니다.

예를 들어 75,000원 × 2주를 76,000원 × 2주로 변경할 때 새 전체 금액은 152,000원입니다. 원주문 예약을 제외한 현재 주문가능현금이 151,999원이면 차액 2,000원을 충당할 수 있어도 앱에서 거절합니다. 152,000원 이상이면 다른 조건과 전송 직전 검사를 통과해야 합니다. 예약금을 재사용하는 더 넓은 증액 허용은 후속 계약 확인 범위입니다.

## 화면 확인

먼저 실제 계좌를 호출하지 않는 시뮬레이터에서 확인합니다.

1. `모의 → 주문 시뮬레이션 → 새 세션`, 시작 현금 302,000원으로 생성합니다. 기본 가정 시세 75,000원·수량 2주·미체결 대기 매수를 승인/전송합니다. 가용 가상 현금은 152,000원입니다.
2. 해당 카드의 `지정가 변경 검토`에서 76,000원을 입력합니다. 승인 창의 기존/새 지정가와 수량 2주를 확인합니다. 별도 최종 체크 전에는 전송되지 않습니다.
3. 대기 정정이 접수되면 원주문 REPLACED, 새 주문 OPEN, 전송 1회, 가용 현금 150,000원을 확인합니다. 실제 가상 현금은 아직 302,000원입니다.
4. 새 주문 2주를 수동 가상 체결하면 현금 150,000원·보유 2주가 됩니다. 같은 명령 재요청은 다시 전송하거나 정산하지 않습니다. 원주문에 추가 정정은 불가합니다.
5. 별도 세션의 시작 현금을 301,999원으로 만들고 같은 원주문을 접수하면 가용 현금 151,999원입니다. 76,000원 정정 준비는 거절되고 원주문 OPEN·변경 미사용·자원 유지가 기준입니다.
6. 준비 후 다른 주문으로 가용 현금을 사용하거나 가정 시세를 허용 범위 밖으로 바꾸면 최종 제출이 거절되어야 합니다. 새 자식은 READY·전송 0회이고 원주문 변경 가드를 소비하지 않습니다.
7. 증액 정정의 `접수 후 응답 유실`도 가상 종결을 지원합니다. 원주문 REPLACED·자식 전량 체결 및 소유권을 확인한 뒤 별도 종결하며 추가 체결/정산은 없습니다. [가상 종결 확인](order-completion-evidence.md)을 따릅니다.

실제 수동 주문은 `보유 → KB 수동 주문 → 접수된 신규 주문 → 지정가 변경`으로 진입합니다. 변경 전후 지정가·동일 수량·매수 증액 현금 조건을 표시하고 별도 체크 후 `실제 주문 전송`을 요청합니다. 실제 테스트 주문이나 환경 스위치는 이번 작업에서 조작하지 않았습니다. 승인 후 부분체결·계좌 변경·만료가 발생하면 기존과 같이 전송을 거절합니다.

## 저장·배포·남은 범위

기존 수동 정정 API의 `{kind:"AMEND",price}`와 승인/제출 계약을 유지합니다. 시뮬레이터도 기존 commands/prepare·confirm·submit 경로를 사용합니다. 추가 테이블·응답 필드·마이그레이션은 없습니다. 최신 백엔드와 Windows 번들이 필요하며 EXE 경로는 `Front/app_version/build/windows/x64/runner/Release/SagoPalgo.exe`입니다. 기존 017~021 운영 적용 여부는 별도 확인이 필요합니다.

UNKNOWN/SENDING 종결 정책은 바꾸지 않습니다. 실제 정정/취소 완료 계약과 잔량·변경 주문 종결, 종료 근거 없는 SENDING 종결, 예약금 재사용 증액·일부 수량 변경·추가 정정, 운영/실계좌 검증과 11번 자동매매는 남아 있습니다.

## 검증 결과

백엔드 전체 476건(실제 격리 MySQL 통합 94건)과 Flutter 전체 186건 통과, 실패/오류/건너뜀 0입니다. Dart 정적 분석 이슈 없음, Windows Release 빌드 성공을 확인했습니다. 매수/매도 증액 정산·정확한 현금 경계·차액/예약금 사용 거절·준비 뒤 현금 감소/시세 변화·동시 정정 한 번 전송·증액 응답 유실 후 가상 종결·미변경 가격·별도 동의를 검증했습니다. 전용 MySQL 컨테이너와 네트워크는 정리했습니다. KB 응답은 모의 데이터이며 실제 운영 접수/체결·계좌 자원 표기의 검증은 남았습니다.

2026-11-02 후속에서 [실제 첫 일부 수량 정정·취소](manual-partial-order-changes.md)를 구현했습니다. 이 문서의 실제 동일 수량 범위는 첫 전량 미체결 NEW에 한해 선택 수량으로 확장됩니다. 증액은 선택 수량의 새 전체 금액을 별도 현금으로 검사하며 예약금 차액 재사용은 미지원입니다.
