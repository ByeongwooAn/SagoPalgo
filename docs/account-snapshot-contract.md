# R1 읽기 전용 KB 계좌 관찰 계약

기준일: 2026-11-02 · 계약 버전: `KB_ACCOUNT_OBSERVATION_V1` · 상태: 백엔드 계약·격리 검증. 실환경 계좌 대조·배포·UI 연결·자동 동기화·영속 원장은 후속입니다.

[최신 로드맵](realtime-trading-roadmap.md)의 R1 첫 구현입니다. R0 문서의 PR #75와 별도로 최신 `develop`에서 분기했습니다. 이 기능은 기존 화면용 계좌 응답의 반올림·누락값 0 치환을 재사용하지 않고, 공식 필드의 제한된 읽기 관찰을 반환합니다. 주문 승인·전송·가드·종결·자본금·보유분을 변경하지 않습니다.

## 1. 조회 API와 실행 범위

`GET /api/v1/kb/accounts/primary/snapshot?orderDate=20261102`

- `orderDate`는 실제 존재하는 `YYYYMMDD` 날짜입니다. 생략하면 서버의 현재 한국 거래일 날짜를 사용합니다. 잘못된 날짜는 외부 호출 전에 HTTP 400으로 거절합니다.
- 명시적으로 이 GET을 호출할 때만 아래 네 조회를 순차 실행합니다. 백그라운드 폴링·자동 재시도·스케줄러는 추가하지 않았습니다.
- 계좌 조회 설정 OFF이면 인증·조회 호출 없이 `DISABLED`를 반환합니다. 설정을 켜거나 실제 계좌 호출을 검증하는 작업은 이번 구현에 포함하지 않았습니다.
- 기존 `/holdings`, `/balances/settlement`, `/balances/execution` 응답과 기존 가져오기·주문 흐름은 그대로 유지합니다.
- 응답은 `Cache-Control: no-store`이며 서버 메모리/DB에 이전 관찰을 캐시하거나 저장하지 않습니다. 재호출은 새로운 관찰 ID와 새 조회를 생성합니다.

| 순서 | 구간 `api` | 요청 범위 | 조회 제한과 완전성 근거 |
|---|---|---|---|
| 1 | `SSQM1801` 보유 | 현재 설정의 조회구분·시장시간·종목 필터 | `nxt_key` 순회, 최대 10페이지·500개 수신 행. 빈 다음키까지 도달했는지 표시 |
| 2 | `SSQM2932` 결제기준 잔고 | 현재 설정의 계좌/상품유형 구분·거래소시세 구분 | 한 응답의 `tl_data_cnt`와 실제 `Record1` 건수 비교. 연속 조회 계약을 추정하지 않음 |
| 3 | `SSQM2952` 체결기준 잔고 | 현재 설정의 거래소시세 구분 | 위와 동일. 결제기준 잔고와 합산하거나 같은 기준 시점으로 취급하지 않음 |
| 4 | `SSQM2341` 주문 관찰 | 지정 주문일, `ccls_clsf=0` 전체 | `nxt_key` 순회, 최대 10페이지·500개 수신 행. 응답 주문일이 다르면 데이터 제외 |

구간별 `scope`에 실제 조회 조건을 반환합니다. `COMPLETE`는 **그 요청 범위의 수신 완료/구조 검사**를 뜻하며 계좌 전체 자산·과거 주문 전체·누락 없는 실계좌와의 일치를 보증하지 않습니다. 보유 조회의 필터나 상품 구분 때문에 대상이 제한될 수 있습니다.

공식 경로와 다른 사용자 지정 holdings/balance 경로이면 새 계약에서는 `UNSUPPORTED_CONTRACT`로 처리합니다. 공식 응답 모델로 다른 API 데이터를 잘못 표기하지 않기 위한 제한이며 기존 API의 사용자 지정 경로 사용은 바꾸지 않습니다.

## 2. 응답 상태와 메타데이터

공통 `ApiResponse.success=true`는 관찰 응답을 반환했다는 뜻입니다. 소비자는 반드시 `data.status`, 각 구간의 `status/completeness/issues`를 확인해야 합니다. 구간 실패·설정 OFF도 관찰 응답은 HTTP 200이고, 요청 날짜 오류는 HTTP 400입니다.

| 필드 | 의미 |
|---|---|
| `contractVersion`, `observationId` | 버전과 이번 관찰의 UUID. 저장된 스냅샷 ID나 주문/확정 토큰이 아님 |
| `provider=KB`, `accountAlias=primary` | 현재 KB 연결의 논리 별칭. 계좌번호·키·계좌 지문은 반환하지 않음 |
| 전체/구간 `startedAt`, `completedAt` | 서버 UTC 기준 읽기 관찰 구간. 여러 조회의 원자적 기준 시각이 아님 |
| `providerProcessTime` | 마지막으로 읽은 페이지의 유효한 `processTime` 문자열. 공개 필드의 시간대 미확정으로 UTC 변환하지 않으며 잔고/가격의 기준 시각도 아님 |
| `atomic=false` | 네 조회와 페이지들은 원자적 계좌 스냅샷이 아님 |
| `usableForTrading=false` | 성공/완전 여부와 무관하게 항상 false. 이 계약 자체로 주문·원장 정산·pending 해제를 허용하지 않음 |
| `pagesRead` | 정상 KB 응답 봉투를 읽은 페이지 수. 실패한 HTTP 시도 횟수와 다름 |
| `receivedRowCount` | 수신 배열의 원래 행 수. 잘못된 행·상한을 넘은 행도 건수에는 포함 |
| `reportedTotalCount` | 잔고의 `tl_data_cnt`. 없는 값·해석 불가는 null이며 수신 건수로 만들어 채우지 않음 |
| `summary`, `rows[].fields` | 공식 필드 allowlist. 요약은 첫 페이지 값이며 페이지별 요약을 합산하지 않음 |
| `issues` | 고정 코드와 공식 필드 이름. 외부 예외 메시지·KB 응답 전문·다음키는 포함하지 않음 |

메타데이터의 null은 공통 JSON 설정에 따라 생략될 수 있습니다. `summary`와 `rows[].fields`의 누락 숫자 키는 명시적인 null로 보존합니다.

### 상태 정의

| 상태 축 | 값 | 의미 |
|---|---|---|
| `status` | `SUCCESS` | 모든 요청 구간이 완전하고 문제 목록이 비어 있음. 계좌/거래 판단 권위는 없음 |
| `status` | `PARTIAL` | 일부 구간 실패 또는 구간의 누락·잘림·구조/값 문제. 이미 읽은 허용 필드는 구간별로 보존 |
| `status` | `FAILED` | 해당 구간에 정상 봉투를 읽지 못함. 전체는 모든 구간 실패 또는 연결 설정 변경 시 |
| `status` | `DISABLED` | 계좌 조회 설정 OFF. 외부 호출 없음 |
| `completeness` | `COMPLETE` | 해당 범위의 다음키 종료 또는 잔고 건수 일치와 검사 통과 |
| `completeness` | `PARTIAL` | 다음 페이지 실패·반복키·페이지/행 상한·잔고 수신 행 부족 등 |
| `completeness` | `UNKNOWN` | 배열/다음키/총건수 누락 등으로 수신 완료를 확인할 수 없음 |
| `completeness` | `INVALID` | 주문일 불일치·잘못된 행/숫자·중복 식별자·건수 모순 등 |

설정·인증·계좌·조회 범위가 도중 변경되면 전체 행/요약을 버리고 `CONTEXT_CHANGED`로 반환합니다. 이전과 다른 계좌의 자료가 한 관찰에 섞여 노출되지 않도록 합니다. 설정값 자체나 지문은 반환하지 않습니다.

## 3. 소수점·누락값 보존

금액/수량을 JSON 숫자나 `double`로 변환하지 않고 십진 문자열로 반환합니다. 문자열의 소수 자릿수를 보존하고 올바른 천 단위 구분자만 제거합니다. 손익의 음수는 허용하되 수량의 음수는 문제로 기록합니다. 부동소수 JSON 숫자는 이미 파싱 중 정밀도를 잃었을 수 있어 `INVALID_NUMBER`로 처리하며, 정수 JSON 숫자만 손실 없이 허용합니다.

다음은 체결기준 잔고 `rows[].fields`의 일부 필드 발췌입니다.

```json
{
  "is_cd": "005930",
  "hld_q": "0",
  "hld_q_p6": "0.123456",
  "ordr_psbl_q_p6": "0.000001",
  "now_prc": null,
  "byng_amt": "1234.560000",
  "val_pl": "-0.000001"
}
```

일반 수량과 P6 수량을 별도 필드로 보존하며 어느 상품에 무엇을 적용할지는 후속 정규화 계약에서 결정합니다. 누락·빈 값·잘못된 숫자는 null이며 오류 여부는 `issues`로 구분합니다. 누락 가격으로 평가금액을 만들거나 실제 0을 다른 계산값으로 교체하지 않습니다. 원본 전체를 반환하지 않고 계좌번호·인증 헤더·응답 메시지·외부 미지정 필드는 제외합니다.

`Record1` 자체가 없으면 명시적인 건수 0이 있을 때만 빈 결과로 인정합니다. 배열이 없다는 이유만으로 ‘보유 없음’이나 ‘주문 없음’을 만들지 않습니다. 다음키의 부재도 빈 다음키와 구분합니다. 중복 식별자는 제거/합산하지 않고 문제를 표시합니다.

## 4. 중단과 한계

- 보유 다음키는 12자, 주문 다음키는 40자까지의 출력 가능한 ASCII를 유지합니다. 공백이 포함된 키도 원래 값으로 전달하며 제어 문자·반복키는 중단합니다.
- 각 구간은 최대 10페이지, 최대 500행만 검사/보존합니다. 잘린 결과는 완전으로 표시하지 않습니다. 두 잔고 조회에 미확인 다음키가 있으면 자동 순회를 추정하지 않습니다.
- 다른 구간 실패 시 성공 구간은 유지합니다. 같은 페이지를 자동 재시도하지 않으며 다음키 진행은 재시도가 아닙니다.
- 페이지와 구간마다 시점이 다르므로 중간 거래·입출금·정정이 발생할 수 있습니다. 원장 대조/거래 사용은 별도 구현이 필요합니다.
- 결과는 영속화되지 않습니다. 실제 프로세스 재시작·DB 복구를 검증한 것이 아니라 서비스 재생성과 반복 조회에서 이전 결과를 재사용하지 않음을 검증했습니다.
- 새 화면·자동 폴링·스케줄러·DB 마이그레이션은 없습니다. 기존 4자리 수량 DB를 소수점 거래용으로 바꾼 작업도 아닙니다.
- KB 응답의 완료 코드 의미를 해석하지 않으며 UNKNOWN/SENDING·예약금·정정 가드를 변경하지 않습니다.

주요 문제 코드: `LOOKUP_FAILED`, `UNSUPPORTED_CONTRACT`, `CONTEXT_CHANGED`, `MISSING_RECORDS`, `MISSING_NEXT_KEY`, `MISSING_COUNT`, `COUNT_MISMATCH`, `INVALID_COUNT`, `INVALID_RECORDS`, `INVALID_ROW`, `MISSING_IDENTITY`, `DUPLICATE_IDENTITY`, `MISSING_FIELD`, `INVALID_NUMBER`, `NEGATIVE_QUANTITY`, `INVALID_PROCESS_TIME`, `INVALID_NEXT_KEY`, `REPEATED_NEXT_KEY`, `SCOPE_MISMATCH`, `PAGE_LIMIT`, `ROW_LIMIT`, `UNSUPPORTED_PAGINATION`, `ACCOUNT_DISABLED`.

## 5. 공식 근거와 검증

2026-11-02 다음 공개 필드 정의를 GET으로 확인했습니다. 인증된 KB 계좌/주문 호출은 실행하지 않았습니다.

- [SSQM1801](https://openapi.kbsec.com/api/apis/catalog/0c27b10f-cd06-4c30-840d-c644df1d609b/tr-list): 일반/주문가능수량, 보유 배열, 요청·응답 다음키.
- [SSQM2932](https://openapi.kbsec.com/api/apis/catalog/dacd5bd7-558c-4741-96c5-22b85108aaa1/tr-list): 결제기준 요약·총건수·일반/P6 수량.
- [SSQM2952](https://openapi.kbsec.com/api/apis/catalog/57bc6bac-8951-4f40-af53-d98ea5408329/tr-list): 체결기준 요약·총건수·일반/P6 수량.
- [SSQM2341](https://openapi.kbsec.com/api/apis/catalog/66998ea3-85f3-4060-bf6d-f88a163eee35/tr-list): 주문일·전체 체결구분·요청/응답 다음키·관찰 수량. 변경 완료 의미는 보류.

검증은 실제 서비스 단위와 controller→서비스→모의 HTTP 서버 경로를 사용합니다. 6자리 수량·소수 문자열·null/0, 건수/배열/다음키 누락, 반복/상한/부분 실패, 잘못된 날짜, 설정 OFF/변경, 민감정보 allowlist, 반복 조회·새 서비스 인스턴스를 포함합니다. 기존 KB 클라이언트 테스트는 기존 첫 페이지의 요청 형식이 변하지 않았는지도 확인합니다.

기존 build 클래스 폴더의 Windows 파일 잠금 때문에 임시 Gradle init script로 `layout.buildDirectory`만 `build-codex-account-snapshot`으로 바꾸어 검증했습니다. 저장소의 빌드 설정은 변경하지 않았습니다. 이 작업의 검증 수치는 [개발 진척도](development-progress.md)에 기록합니다.

전체 백엔드 테스트 548건 중 **450건 통과**, 실패/오류 0, 전용 MySQL 실행 플래그가 없는 통합 테스트 98건은 건너뛰었습니다. 신규 서비스 33건·HTTP 계약 6건은 모두 실행/통과했습니다. 이 작업은 DB 저장 경로를 추가하지 않아 MySQL 통합 테스트를 별도로 활성화하지 않았습니다.

## 6. 다음 범위

계좌별 관찰 저장·조회 완전성의 실환경 대조, 관찰 간 차이·일별 자산/현금흐름 원장, 앱 화면 연결을 별도 단계로 진행합니다. 스냅샷을 주문 가능 현금으로 자동 승격하거나 관찰에서 사라진 주문/종목을 종결/매도로 추정하지 않습니다.
