# 원주문 추가 대조와 가상 주문 종결

기준일: 2026-11-01. PR #67 이후 작업입니다. 실계좌의 정정·취소 완료 코드 근거를 재조사하고, 원주문까지 포함한 관찰 대조와 **시뮬레이터 전용** UNKNOWN 종결을 추가했습니다. 실계좌 완료 판정·차단 해제는 구현 완료로 계산하지 않습니다.

## 공식 코드 조사 결과

확인한 공개 자료에서는 `crct_cncl_ccd`의 값별 의미와 정정/취소 완료 조건을 찾지 못했습니다. 공개 자료 전체에 존재하지 않는다고 단정하지 않습니다. 다음 경로를 확인했습니다.

| 공식 출처 | 확인 내용과 한계 |
|---|---|
| [SSQM2341 상세 JSON](https://openapi.kbsec.com/api/apis/catalog/66998ea3-85f3-4060-bf6d-f88a163eee35/tr-list) | `crct_cncl_ccd`는 정정취소구분코드, String(15). description은 null. 원주문번호·정정 수량·SOR 취소 수량은 있으나 완료 코드값 설명 없음 |
| [SSQM2341 Excel 다운로드](https://openapi.kbsec.com/api/kbs/guide/excel/5752f3c5-8581-4d0b-bf8a-a2d9615dd229) | 해당 구분 필드의 설명 칸이 비어 있고 파일 내 별도 주석도 확인되지 않음 |
| [공식 전체 JSON 다운로드](https://openapi.kbsec.com/api/kbs/guide/json/b2c) | ZIP의 SSQM2341 공개 샘플은 Record1 빈 배열이며, 완료된 변경 주문의 유효 예제가 아님 |
| [KB 공식 저장소](https://github.com/kbsecurities/kb-openapi) | 전체 파일 목록·예제와 생성된 샘플에서 해당 응답 코드값의 판정표를 찾지 못함 |
| [공식 포털 API 목록](https://openapi.kbsec.com/apidoc_b2c) | 국내주식 관련 목록·정정/취소 및 체결미체결 상세 정의 확인. 별도의 완료 조회 근거는 확보하지 못함 |

요청 `crct_clsf`와 응답 `crct_cncl_ccd`는 서로 다른 필드입니다. [정정 요청 정의](https://openapi.kbsec.com/api/apis/catalog/28577def-666f-4d77-b9dc-5904db58ba49/tr-list)와 [취소 요청 정의](https://openapi.kbsec.com/api/apis/catalog/48815fb5-53fd-4b58-905b-c04431a1e882/tr-list)의 일부/전부 구분 값을 응답의 성공/취소 코드에 옮기지 않습니다. 다른 증권사의 코드도 적용하지 않습니다. `sor_cncl_q`를 KRX 전체 취소 수량으로 사용하지 않습니다.

실계좌 완료 판정을 진행하려면 KB의 공식 설명이나 확인 가능한 응답 계약이 더 필요합니다. 개발 중 실제 계좌 조회·주문을 수행하거나 KB에 메시지를 전송하지 않았습니다.

## 실계좌 대조 보강

UNKNOWN 정정/취소의 기존 대조 준비·확인에서 자식 행뿐 아니라 **저장된 원주문번호로 원주문 행도 별도 조회**합니다. 조회 중 DB 잠금은 유지하지 않습니다.

- 요청 범위·전체 페이지·단일 행·번호/종목/방향/지정가/수량/시각·거절 사유와 수량 범위를 확인합니다.
- 일치하면 `parentObservation.verification=REFERENCE_MATCH`와 원주문의 체결·잔량·정정/SOR 취소 수량을 관찰에 추가합니다. 이 참조 일치는 완료 판정이 아닙니다.
- 범위 불일치·불완전·중복·항목 불일치·수량 오류·조회 실패는 각각 구분해 보관하고, 확인하지 못한 행이나 원문 예외를 저장하지 않습니다.
- 부모 관찰도 준비/확인 해시에 포함합니다. 자식이 그대로여도 부모 관찰이 바뀌면 저장을 거절하고 다시 준비하도록 합니다. 실패했던 부모 조회가 성공한 경우도 관찰 변경입니다.
- 두 조회는 증권사의 원자적 스냅샷이 아니므로 동시 변화 가능성이 있습니다. 재조회와 관찰 저장을 완료 근거로 승격하지 않습니다. 계좌 변경은 저장 전에 다시 거절합니다.

기존 `보유 → KB 수동 주문 → 정정·취소 주문 대조`에서 원주문 추가 조회 결과를 확인할 수 있습니다. 기존 이력에 `parentObservation`이 없으면 조회하지 않은 과거 이력으로 표시합니다. 기존 90초 준비는 배포 후 해시가 달라질 수 있으므로 다시 준비합니다. 실계좌 pending 집계와 상태·전송/변경 가드·보유/자본금은 변경하지 않습니다.

## 시뮬레이터 전용 종결

가상 증권사는 자체 주문 소유권과 REPLACED/CANCELLED/FILLED 상태를 명시적으로 보관할 수 있습니다. 이 내부 근거만으로 다음 세 경우를 종결합니다. KB 응답 코드 또는 클라이언트가 전달한 source 플래그는 근거가 아닙니다.

| 가상 명령 | 필요한 종결 근거 |
|---|---|
| NEW | 호출 종료 RETURNED/UNKNOWN, 전송 1회·실행 소유권·가상 주문/명령 일치, 전량 체결·잔량 0 |
| AMEND | 위 소유권과 알려진 원주문·해당 자식의 변경 사용 기록, 부모 REPLACED·체결/잔량 0, 다른 지정가·동일 수량, 자식 전량 체결. [제한적 증액 후속](order-price-amendment.md) 포함 |
| CANCEL | 위 소유권과 원주문/자식 연결, 부모·자식 모두 명시적 CANCELLED·체결/잔량 0·동일 수량/지정가 |

신규 90초 토큰과 종결 근거 해시를 준비하고 별도 체크 후 확정합니다. 최종 검사에서 근거·토큰·소유권·기한을 다시 확인합니다. 저장과 토큰 소비는 가상 세션의 단일 트랜잭션이며 실패 시 모두 롤백합니다. 같은 확정은 한 번만 감사 기록을 남기고 저장된 결과를 반환합니다.

확정해도 원래 명령 상태 UNKNOWN, 전송 횟수, 부모 변경 사용 기록, 가상 현금/보유는 유지합니다. 별도 `completion` 기록으로 이 명령만 pending에서 제외합니다. 다른 SENDING/미종결 UNKNOWN은 계속 차단합니다. 같은 명령을 재제출해도 추가 전송하지 않습니다. 이후 새 가상 주문은 기존 가정 시세·금액·예약 제외 자원 검사부터 다시 거칩니다.

SENDING, 미체결·부분체결, 증권사 주문 없음, 실행 종료/소유권 없음, 부모/자식 불일치는 종결하지 않습니다. 이전 JSON에 changeKind·원주문/변경 소유권 같은 필수 근거가 없으면 새 근거를 만들지 않고 차단합니다. 새 세션에서 검증하세요. 유효하지 않은 완료 기록이나 SIMULATION이 아닌 출처도 차단 제외에 사용하지 않습니다.

### 화면 확인 순서

1. `모의 → 주문 시뮬레이션`에서 새 세션을 생성합니다. `접수 후 응답 유실` 신규 매수로 UNKNOWN·가상 FILLED·전송 1회를 만듭니다.
2. `가상 주문 종결 대조`에서 표시된 번호로 `가상 종결 근거 확인`을 누릅니다. 체크 전에는 `가상 종결 확정`을 실행할 수 없습니다.
3. 가상 근거와 해당 명령의 차단 해소를 확인한 뒤 확정합니다. 원본 UNKNOWN·전송 1회·현금/보유가 유지되고, 가상 종결 이력이 저장되어야 합니다. 다른 미확정 명령이 없으면 신규 가상 주문 버튼이 열립니다.
4. 별도 세션에서 대기 신규 주문 → 가격 인하 또는 전부 취소를 `접수 후 응답 유실`로 실행해 자식 UNKNOWN을 종결합니다. 원주문 변경 사용 기록은 유지되어야 합니다.
5. `부분체결 후 응답 유실`은 바로 종결할 수 없습니다. 수동 가상 체결로 잔량을 모두 체결한 뒤 종결하고, 종결 자체가 추가 체결/잔액 변경을 하지 않는지 확인합니다.
6. 응답 유실 뒤에는 `가상 종결 이력 새로고침`으로 GET 확인만 합니다. 확인한 가상 출처·명령의 완료 기록으로만 화면 대기 표시를 정리하고 원래 주문/확인 POST를 자동 반복하지 않습니다.

실제 수동 주문 화면에는 가상 종결 버튼이나 완료 확정 API를 추가하지 않았습니다. 가상 토큰·확인 문구는 실계좌 대조 확인에도 사용할 수 없습니다.

## API·저장·배포

새 API는 `/api/v1/orders/simulations/{sessionId}/commands/{id}/completion` 아래에만 있습니다.

- POST `/prepare`: `{orderNo}` → `{mode:"SIMULATION",resolutionId,token,expiresAt,evidence,message}`.
- POST `/confirm`: `{resolutionId,token,acknowledged:true,confirmation:"가상 주문 종결 확정"}` → 세션 상태.
- 기존 세션 GET은 명령의 `resolved`와 검증된 `completion`을 반환합니다. 완료 기록은 resolutionId·evidence·confirmedAt·lockMaintained:false·source:SIMULATION만 포함합니다. 토큰/근거 해시·실행 키·내부 준비는 반환하지 않습니다.

실계좌 관찰은 기존 021 JSON에 선택적 `parentObservation`을 추가하고, 가상 종결은 기존 018 세션 JSON을 사용합니다. **새 DB 마이그레이션은 없습니다.** 기존 017~021 적용과 최신 백엔드·EXE가 필요하며 적용 완료는 별도 확인 사항입니다. 운영 DB·설정·실제 계좌는 이번 작업에서 변경하지 않았습니다.

EXE는 `Front/app_version/build/windows/x64/runner/Release/SagoPalgo.exe`로 동일합니다. 새 Flutter 번들까지 함께 사용합니다.

## KB에 확인할 질문 초안

사용자가 공식 Q&A 등에 전달할 수 있는 초안이며 에이전트가 발송하지 않았습니다. 계좌번호·인증값·개인 주문 원문을 포함할 필요가 없습니다.

> SSQM2341의 crct_cncl_ccd가 가질 수 있는 값과 각 값의 의미, 접수·거절·완료 구분을 확인 부탁드립니다. orgn_ordr_no는 직전 주문과 최초 주문 중 어느 번호인지, 변경 행의 ordr_q/tl_ccls_q/nccls_q가 해당 주문 단독인지 전체 연결 주문 누적인지도 궁금합니다. crct_q는 정정과 취소를 모두 포함하는지, KRX 전부 취소 완료 수량을 확인할 수 있는 필드는 무엇인지 확인 부탁드립니다. sor_cncl_q 외의 근거와, 취소 접수/완료 및 조회 반영 지연을 구분하는 공식 기준이나 비식별 예제가 있으면 안내 부탁드립니다.

## 남은 작업

실계좌 정정·취소 완료 계약 확보와 검증, 잔량/변경 주문·종료 근거 없는 SENDING 종결, 추가 정정/예약금 재사용 증액/일부 수량 변경, 운영 배포·화면·실계좌 검증, 11번 자동매매는 남았습니다. 지정가 증액은 후속에서 별도 가용 현금으로 새 전체 금액을 충당하는 제한 범위만 구현했습니다. 가상 종결을 실계좌 종결 완료로 계산하지 않습니다.

## 자동 검증 결과

백엔드 462건(실제 격리 MySQL 87건), Flutter 182건 통과, Dart 정적 분석 이슈 없음, Windows Release 빌드 성공입니다. 부모 단독 변화/조회 실패·기존 JSON, 가상 종결 소유권·잘못된 출처·부분체결 차단·잔량 체결 후 종결, 만료/토큰 교체·동시 확인·저장 실패 롤백·다른 SENDING 차단과 응답 유실 GET 복구를 확인했습니다. 전용 MySQL 테스트 컨테이너·네트워크는 정리했습니다. 실제 KB의 코드 의미·운영 계좌 응답·실주문 성공을 검증한 것은 아닙니다.

2026-11-02 재조사에서도 SSQM2341의 crct_cncl_ccd/crct_q/sor_cncl_q 설명은 null로 확인했습니다. 요청 구분의 공식 일부/전부 정의를 이용한 [첫 일부 수량 변경](manual-partial-order-changes.md)은 지원하지만 실제 완료 코드·추가 변경 계보·예약금 재사용 계약을 대체하지 않습니다. 메인 PC는 이후 022 적용·새 백엔드/앱 빌드·DB/GET 점검을 완료했으며 실제 주문 결과 대조는 별도입니다.
