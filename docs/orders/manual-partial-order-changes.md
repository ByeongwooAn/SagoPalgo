# 실제 주문의 제한적 일부 수량 정정·취소

기준일: 2026-11-02. 남은 작업 4번 중 **당일 전량 미체결 신규 주문의 첫 변경**을 선택 수량으로 확장했습니다. 추가 정정·부분체결 이후 변경·실제 예약금 재사용과 변경 완료 판정은 계속 미지원입니다.

## 확인한 공식 계약

2026-11-02 KB 공식 상세 JSON을 다시 조회했습니다.

- [SSAM1805 정정 요청](https://openapi.kbsec.com/api/apis/catalog/28577def-666f-4d77-b9dc-5904db58ba49/tr-list)의 요청 crct_clsf는 1 일부/2 전부이며 ordr_q는 일부 정정 시 입력하는 수량입니다.
- [SSAM1806 취소 요청](https://openapi.kbsec.com/api/apis/catalog/48815fb5-53fd-4b58-905b-c04431a1e882/tr-list)에도 일부/전부 구분과 주문수량·원주문번호가 있습니다.
- [SSQM2341 조회 정의](https://openapi.kbsec.com/api/apis/catalog/66998ea3-85f3-4060-bf6d-f88a163eee35/tr-list)의 crct_cncl_ccd, crct_q, sor_cncl_q 설명은 여전히 null입니다. 요청 구분을 응답 완료 코드로 해석하지 않습니다. 추가 정정 계보·주문별 예약금 반환 계약도 확보되지 않았습니다.

문서화된 첫 변경 요청만 확장하고, 완료 판정이 필요한 차단 해제나 추가 변경은 열지 않습니다. 외부 조사 중 실제 KB 계좌 API를 호출하거나 문의를 발송하지 않았습니다.

## 허용 범위와 수량의 의미

ACCEPTED인 당일 NEW, 변경 가드 미사용, 전체 조회의 정확한 주문일/주문번호·단일 행·종목/방향/가격/원수량과 전량 미체결을 확인해야 합니다. OPEN 표기만 믿지 않고 체결 0·잔량=원수량·거절 사유 없음·기존 정정/취소 근거 없음도 검사합니다. 준비와 제출 직전에 다시 확인하며 제출 가드와 단일 전송을 유지합니다.

선택 수량은 새 총수량이 아니라 **다른 가격으로 옮기거나 취소할 수량**입니다. 5주 중 2주 정정은 기존 가격에 3주가 남고 새 가격으로 2주를 요청하는 의미입니다. 취소는 선택 2주만 대상으로 하며 수량 증가는 신규 주문입니다. 0·음수·소수·원수량 초과는 준비 전 거절합니다.

요청량이 원수량보다 작으면 crct_clsf=1, 같으면 2이며 ordr_q는 선택 수량입니다. parent_id와 자식 quantity에 승인 범위를 고정합니다. 원본 수량은 바꾸지 않고 변경 가드는 한 차례 소비한 채 보존합니다. 남은 3주나 정정 자식의 추가 변경은 앱에서 허용하지 않습니다.

매수 증액은 선택 수량의 새 지정가×수량 **전체 금액** 이상의 현재 주문가능현금과 BUYING_POWER 성공을 준비·제출 시 모두 요구합니다. 기존 예약금/차액을 합산하지 않습니다. 예를 들어 75,000원×5주 중 2주를 76,000원으로 올리려면 추가 주문가능현금 152,000원 이상을 확인합니다. 2,000원 차액만으로 통과시키지 않습니다. 기존 인하·매도 정정의 예약 자원 검증 정책은 유지합니다.

ACCEPTED는 접수 응답이며 완료가 아닙니다. UNKNOWN 일부 변경은 원주문과 선택 수량의 대조 관찰만 저장하고 상태·pending·제출/변경 가드를 유지합니다. 확인되지 않은 수량/계보를 임의로 맞춰 종결하지 않습니다. 보유·자본금·가상 자원을 변경하지 않습니다.

## 화면과 API

`보유 → KB 수동 주문 → 기존 신규 접수 주문`에서 `지정가 변경` 또는 `수량 취소`를 선택합니다. 정정/취소할 수량을 입력하고 준비하면 선택 수량·기존 가격에 남을 예정 수량·새 가격·금액을 표시합니다. 실제 주문 전송은 별도 체크 후에만 가능합니다. 취소/입력 오류/서버 주문안 불일치는 전송하지 않습니다. 실제 시험 주문을 만들지 않고 UI와 HTTP는 모의 응답으로 검증했습니다.

기존 POST `/api/v1/orders/manual/{id}/changes/prepare`의 본문은 `{kind,price?,quantity?,reuseReservation:false}`입니다. quantity 누락은 기존 전량 요청과 호환됩니다. reuseReservation=true는 계속 거절합니다. 제출은 기존 자식 submit 경로·90초 토큰·별도 동의를 사용합니다. 새 API 경로나 DB 마이그레이션은 없습니다.

앱은 서버가 반환한 PREPARED 주문의 부모·종목·시장·방향·종류·가격·선택 수량이 모두 일치해야 최종 동의를 엽니다. 이전 서버가 선택 수량을 무시해 전량 주문안을 반환해도 전송하지 않습니다. 응답 유실은 GET으로만 재조회하며 추가 정정/취소 POST를 자동 반복하지 않습니다.

## 배포 점검과 검증

메인 PC DB는 2026-11-02 백업 후 022 적용·컬럼/PK/FK/ABORTED CHECK·수동 이력 GET 200 확인을 완료했습니다. 사용자의 일반 앱 구동 확인도 반영합니다. 017~021 또는 022 미확인이라는 과거 문구는 당시 상태입니다. Ubuntu의 별도 DB나 실제 주문·장기 운영 검증으로 확대하지 않습니다.

재사용 가능한 읽기 전용 점검을 추가했습니다.

```powershell
./scripts/check-manual-order-deployment.ps1 -ApiBaseUrl http://localhost:8080
```

016~021 테이블 존재, 022의 필수 컬럼/키/단계 CHECK와 주문 저장소 준비·이력 GET을 검사합니다. 실패는 종료 코드 1이며 인증값·계좌/주문 원문을 출력하지 않습니다. GET과 DB 메타데이터만 사용하고 실제 주문/시뮬레이터 POST·KB 조회·스위치 변경은 없습니다. 실주문 스위치 상태는 별도 사실로 표시하며 OFF여도 배포 점검은 통과할 수 있습니다. 이 점검만으로 일부 변경 코드 배포 버전이나 실제 거래 성공을 확정하지 않습니다.

백엔드 552건(격리 MySQL 141건)·Flutter 206건 통과, 앱 소스/테스트 Dart 분석 이슈 없음, localhost:8080용 Windows Release 빌드 성공. 선택 수량의 매수/매도·정정/취소/전량 인코딩, 준비 뒤 현금 부족·잘못된 OPEN/일자/번호·초과 수량, 동일 부모 동시 예약 한 건과 UNKNOWN 부분 변경의 잠금 유지, 서버 주문안 불일치·별도 동의·응답 유실을 검증했습니다. 전용 테스트 MySQL/네트워크를 정리했습니다.

새 Spring API 컨테이너 반영 후 읽기 전용 배포 점검 11개가 통과했고 실주문 OFF를 확인했습니다. 연결할 수 없는 API 주소에서는 실패 결과와 종료 코드 1을 확인했습니다. 실행 파일은 기존 `Front/app_version/build/windows/x64/runner/Release/SagoPalgo.exe`이며 DLL/data를 포함한 같은 폴더 번들로 사용합니다. 실제 주문은 실행하지 않았습니다.
