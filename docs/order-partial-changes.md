# 추가 정정·수량 배분·예약금 재사용

기준일: 2026-11-01. 요청한 남은 작업 4·5번 중 **시뮬레이터 구현·검증 범위**입니다. 실제 KB의 추가 정정·일부 수량 변경·예약금 재사용 전송은 아직 지원하지 않습니다. 실제 경로는 기존 당일 전량 미체결 신규 주문의 한 차례·동일 수량 정정과 보수적 증액 조건을 유지합니다.

## 공식 계약 확인과 남은 근거

- [SSAM1805 정정 정의](https://openapi.kbsec.com/api/apis/catalog/28577def-666f-4d77-b9dc-5904db58ba49/tr-list)는 `crct_clsf=1` 일부/`2` 전부, 일부 정정의 주문수량, 새 지정가·원주문번호를 제공합니다.
- [SSAM1806 취소 정의](https://openapi.kbsec.com/api/apis/catalog/48815fb5-53fd-4b58-905b-c04431a1e882/tr-list)도 일부/전부 구분과 수량·원주문번호를 제공합니다.
- [SSQM1802 매수주문가능금액](https://openapi.kbsec.com/api/apis/catalog/8225252f-36c7-47e3-8ec0-4fca5687fabc/tr-list)의 입력은 종목번호입니다. 주문별 원주문번호·예약금 식별/반환 조건을 확인하는 요청은 확인되지 않았으며 응답 금액의 관련 설명도 비어 있습니다.
- [공식 API 목록](https://openapi.kbsec.com/apidoc_b2c)과 위 정의만으로는 정정 이후 어떤 주문번호를 다음 변경의 원주문으로 사용하는지, 원주문 잔량/수량이 개별인지 누적인지, 증거금·수수료·예약금 재사용 범위를 확정하지 못했습니다. 공개 자료 전체에 없다고 단정하지 않습니다.

따라서 `기존 지정가×수량`을 실제 KB의 재사용 가능한 예약금으로 간주하지 않습니다. 실계좌 확장에는 주문별 변경 가능 잔량/자원과 정정 계보·거절/미확정 결과 처리에 대한 KB의 공식 설명 또는 확인 가능한 계약이 필요합니다. 문의나 실제 조회/주문을 발송하지 않았습니다.

## 가상 모델

일부 정정 수량은 **새 총 주문수량이 아닌 다른 가격으로 옮길 수량**입니다. 기존 5주 중 2주 정정은 기존 가격 3주와 새 가격 2주로 나뉘어 총수량 5주를 유지합니다. 전체 수량을 줄이려면 일부 취소를 사용합니다. 수량 증가는 신규 주문으로 진행합니다.

가상 증권사 주문은 원래 수량·체결 수량·정정/취소 배분 수량·잔량을 보존합니다. OPEN/PARTIAL 잔량은 `원래 수량 - 체결 수량 - 배분 수량`이며 배분 맵은 자식 명령별 수량을 기록합니다. 내부 revision과 마지막 변경 명령을 보관합니다. 상태가 FILLED여도 이전 배분이 있으면 원래 전체 수량의 체결을 뜻하지 않으므로 화면에서 체결/잔량/배분을 함께 확인합니다.

변경 대상은 사용자 소유 세션에서 정상 접수된 NEW/AMEND의 현재 잔량입니다. 전송 종료·1회 전송·접수 결과의 주문번호·가상 주문 소유권·기존 배분 합계를 확인합니다. 이전 변경이 정상 접수되고 배분이 일치하면 남은 부모 또는 정정 자식에서 다음 변경을 준비할 수 있습니다. 부분체결 후에도 잔량 이내에서 가능합니다. CANCEL 명령 자체는 변경하지 않습니다.

준비는 부모 주문번호·체결/배분/잔량·revision·이전 변경 명령을 고정합니다. 제출 직전 동일 근거·90초 기한·가정 시세/이탈률·금액 한도·자원을 다시 검사하고 세션 행 잠금 아래 단일 변경을 예약합니다. 같은 잔량을 본 동시 승인은 하나만 통과하며 다른 승인은 새로 준비해야 합니다. 가상 증권사 처리 직전에 근거가 달라져도 거절하고 예약 가드를 유지합니다. 원래 명령의 재제출은 추가 전송하지 않습니다.

가상 매수 예약금은 **선택한 잔량의 기존 지정가×수량만** 재사용합니다. 추가 현금은 `max(0, 새 지정가×선택 수량 - 기존 지정가×선택 수량)`입니다. 인하/취소의 차액만 가용 금액에 풀고 가상 현금 자체는 체결 때만 변경합니다. 매도 예약 주식은 선택 수량만 이동/취소하며 현금으로 바꾸지 않습니다. 나머지 주문과 다른 종목의 예약금을 합산하지 않습니다.

거절·SENDING·미종결 UNKNOWN의 변경 가드를 자동 해제하지 않습니다. 정상 접수/배분 근거가 있어야 다음 변경을 허용하며 가상 종결 이력만으로 원주문 변경 가드를 해제하지 않습니다. 부분 정정/취소의 UNKNOWN은 해당 자식의 종료·배분·전량 체결/명시적 취소를 확인하는 별도 가상 종결로 신규 주문 차단만 해소합니다. 부모에 남은 잔량은 계속 예약됩니다.

## 화면 확인

1. `모의 → 주문 시뮬레이션 → 새 세션`을 열고 375,000원·75,000원×5주를 미체결 대기로 접수합니다. 가용 현금은 0원입니다.
2. `지정가 변경 검토`에서 74,000원·정정할 수량 2주를 입력합니다. 기존 3주가 남고 새 2주가 생긴다는 안내와 가상 재사용 150,000원·추가 0원·해제 예정 2,000원을 확인합니다. 별도 최종 동의 후 부모 잔량 3주/배분 2주, 자식 잔량 2주, 가용 현금 2,000원이 기준입니다.
3. 새 자식에서 76,000원·1주를 추가 정정하면 차액 2,000원을 사용합니다. 자식에는 74,000원 1주가 남고 새 76,000원 1주가 생겨 가용 현금이 0원이 됩니다. 원래 75,000원 3주도 남습니다.
4. `수량 취소 검토`에서 원하는 주문의 1주를 취소합니다. 취소 수량만 예약에서 빠지며 체결하지 않은 현금·보유분은 변하지 않습니다. 원주문 가격의 남은 수량과 분리해 확인합니다.
5. 별도 152,000원 세션의 75,000원×2주 주문을 76,000원×2주로 변경하면 기존 150,000원 예약과 차액 2,000원으로 통과합니다. 151,999원 세션은 차액이 1원 부족해 거절되어야 합니다. 이 정책은 시뮬레이터 전용입니다.
6. 변경 준비 후 부모를 수동 체결하거나 다른 부분 변경을 먼저 전송하면 기존 승인은 거절되어야 합니다. 같은 스냅샷의 동시 변경은 한 번만 처리됩니다. 잔량 초과·0·소수 수량도 거절합니다.
7. 일부 변경을 접수 후 응답 유실로 실행하고 가상 종결을 확인합니다. 자식 배분 근거와 완료 이력은 저장하지만 부모 잔량·현금/보유·전송 횟수는 바꾸지 않습니다. 거절·불명확한 변경 뒤에는 해당 원주문 변경 가드를 유지합니다.

## API·호환성·배포

기존 시뮬레이터 commands/prepare의 `plan.quantity`를 선택 수량으로 사용합니다. AMEND는 새 지정가·선택 수량, CANCEL은 선택 수량이며 가격은 서버가 부모 가격으로 고정합니다. 종목·시장·방향은 부모에서 가져옵니다. 신규 주문·기존 실주문 API를 대신 호출하지 않습니다.

세션 GET에 `changePolicy:"OWNED_RESERVATION_V1"`, 명령에 `changeable,removedQuantity,changeBudget`을 제공합니다. changeBudget은 `selectedQuantity,remainingQuantity,reusedCash,newReservedCash,additionalCash,releasedCash,scope(ALL/PARTIAL)`입니다. 앱은 정책 식별자가 없으면 변경 준비를 차단하고, 준비 응답의 종류·부모·종목/시장/방향·지정가/수량이 입력과 다르면 승인하지 않습니다. 내부 부모 스냅샷·실행 키·토큰 해시를 반환하지 않습니다.

실제 changes/prepare는 선택적 `quantity,reuseReservation`을 명시적으로 읽습니다. 다른 수량 또는 reuseReservation=true는 400으로 거절하며 조회/전송/승인을 시작하지 않습니다. 기존 본문 또는 동일 수량·false는 기존 규칙을 따릅니다. 실제 증액 UNKNOWN의 대조 관찰이 인하 전용 조건으로 막히던 오류도 수정했지만 상태/차단은 계속 유지합니다.

새 마이그레이션은 없습니다. 기존 018 JSON에 스냅샷·배분/리비전을 추가하고 종결 관찰에 선택적 배분 근거를 저장합니다. 이전 JSON의 누락 필드는 기본값/null로 읽으며, 필수 소유권이 없거나 이전 변경 가드를 입증하지 못하면 새 변경을 열지 않습니다. 이전 준비의 스냅샷이 없으면 기존 전체 금액 검증을 유지하고 예약 재사용을 부여하지 않습니다. 진행 중인 90초 가상 종결 준비는 배포 후 다시 준비해야 할 수 있습니다. 최신 백엔드와 Windows 번들을 함께 사용합니다. 017~021 운영 적용 확인은 여전히 별도입니다.

실제 4·5번 전체 완료로 처리하지 않습니다. 실제 KB 확장에는 위 공식 계약 확보와 이후 별도 구현·운영 검증이 남아 있으며 자동매매도 미착수입니다.

## 최종 검증 결과

백엔드 전체 503건(실제 격리 MySQL 통합 111건), Flutter 전체 191건 통과이며 실패/오류/건너뜀은 0입니다. Dart 정적 분석 이슈 없음, Windows Release 빌드 성공을 확인했습니다. 매수/매도 일부 정정의 수량·현금 보존, 부분체결 뒤 일부 취소, 추가 정정 계보, 선택 예약금 차액과 1원 부족 경계, 동시 스냅샷 단일 소비·준비 후 체결/변경 거절, 잘못된 소유권/배분, UNKNOWN 부분/추가 변경 종결, 실제 HTTP 입력 차단과 증액 대조의 pending 유지, 구형 서버/반환 주문안 불일치 차단을 검증했습니다. JSON 숫자 scale 차이와 이전 승인에 부분체결 권한을 소급하지 않는 조건도 확인했습니다. 전용 테스트 MySQL 컨테이너·네트워크는 검증 후 정리했습니다. 실제 KB 접수/체결·운영 DB·설정 변경은 실행하지 않았습니다.
