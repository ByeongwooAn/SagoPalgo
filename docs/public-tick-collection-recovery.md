# 실제 틱·호가 자료 부재 원인과 복구

확인일: 2026-11-06, 한국 시간. [직전 입력 규격 작업](tick-reference-validation.md)의 실제 자료 부재를 해소했습니다. **실제 자료 확보·입력 무결성 대조 완료**이며 내 주문 체결·과거 CB 틱·장기 정상 수집까지 완료한 것은 아닙니다.

## 원인 분리

1. LAN/루프백의 저장 export는 HTTP 502·`EXTERNAL_DATA_ERROR`였습니다. Nginx 자체 health는 200이고 Spring의 GET 요청까지 도달했습니다. 따라서 프록시 중단이 직접 원인이 아니었습니다. Spring `/health`의 500도 Nginx health와 다른 경로이므로 앱 API 상태로 확대하지 않습니다.
2. `StoredDatasetExportService`가 읽는 `market_stream_events`와 `research_versions`를 포함해 **025의 2개·026의 4개 테이블이 모두 없었습니다.** 스키마 초기화는 새 DB 생성 때만 실행되며 기존 DB에 신규 schema.sql 변경이 자동 반영되지 않습니다.
3. 운영 서버의 스트림 활성화·권한 확인은 true가 아니고 승인 구독 예산은 양수가 아니었습니다. 수집이 실행되지 않았으므로 일봉만 있고 틱/호가가 없는 상태였습니다. KIS 자체 미지원이나 개인용 분석 이용 금지로 판단한 결과가 아닙니다.
4. 최초 DB 재진단 과정에서는 Windows 표준입력 CRLF로 SQL 종료 표식이 깨지는 오류를 별도로 확인했습니다. 바이트 LF 입력·명령 종료 코드·정확한 결과 행 수 검사로 재확인했습니다. SQL 오류나 빈 출력을 테이블 없음/점검 성공으로 처리하지 않습니다.

## 백업·적용·API 복구

- 운영 DB 전체를 `Back/spring-server/build-codex-tick-readiness/before-025-026-20261106T022558Z.sql.gz`에 백업했습니다. 압축 전후 바이트 일치와 SHA-256을 검증한 후 기존 [025](../Back/database/migrations/025_market_stream.sql)·[026](../Back/database/migrations/026_research_incremental.sql)을 순서대로 적용했습니다.
- 적용 후 `GET /api/v1/research/dataset-export`는 **HTTP 200, export V1**으로 복구됐습니다. 자료가 없을 때 200·빈 목록과 저장소 실패 502를 구분합니다. `GET /api/v1/market/realtime`도 200·DISABLED입니다.
- 수집 전후 mysqldump의 기존 테이블 구간을 비교해 **원래 32개 테이블 동일, 추가 6개**를 확인했습니다. 비교는 계좌/주문 등 기존 데이터 원문을 출력하지 않고 로컬에서 수행했습니다.
- 기존 서버의 재배포·재시작·환경 변경은 하지 않았습니다. 일반 운영 수집은 OFF를 유지합니다. 백업과 실제 시세는 Git 제외 경로에만 보존합니다.

## 실제 제한 수집과 대조

사용자는 동일 KIS 키를 다른 프로그램에서 사용하지 않는다고 확인했습니다. 기존 개인 로컬 분석 범위와 이 확인에 따라 **삼성전자 005930, 체결 H0STCNT0·호가 H0STASP0 총 2개 구독**으로 시험했습니다. [공식 체결/호가 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_user/domestic_stock/domestic_stock_functions_ws.py)·[구독 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_user/kis_auth.py)를 대조했으며 예제의 40개 상한을 이 계정의 운영 승인 한도로 간주하지 않습니다. 이번 확인 범위는 실제 승인·수신된 2개뿐입니다.

- 기존 서버와 별도인 루프백 18080의 일회성 Spring 수집기를 사용했습니다. DB와 공개 KIS 설정만 주입하고 KB 계좌/주문/실주문·AI·뉴스/계좌 자동 수집은 OFF, 시작 대기와 구분한 관찰 루프는 30초로 제한했습니다.
- 최초 시도는 실행 중 컨테이너가 참조하는 이미지 ID가 로컬 이미지 저장소에 없어 **외부 연결 전에 실패**했습니다. 다음 시도에서는 이미 로컬에 빌드된 백엔드 태그를 `--pull=never`로 사용했습니다. 기존 운영 이미지/컨테이너를 교체하지 않았습니다.
- 시작~종료는 **11:28:46~11:29:23 KST**, 시작 대기를 제외한 관찰 루프 30초입니다. 부트 중 초기 수신을 포함한 실제 첫~마지막 수신은 **11:28:50.699248~11:29:22.832452, 32.133204초**로, 총 수신 시간이 정확히 30초였다고 표시하지 않습니다. 종료 시 CONNECTED/LIVE, 체결·호가 모두 수신을 확인했고 수집기를 정상 종료했습니다. 임시 환경 파일은 삭제됐고 컨테이너는 자동 제거됐습니다. 운영 OFF와 별도로 단기 수집이 수행됐음을 구분합니다.
- 완료된 `[11:28,11:30)` 구간을 기존 운영 API로 내보냈습니다. **실제 체결 946·호가 135, 합계 1,081행**입니다. 전체 2분 동안의 완전한 시세가 아니라 그 안에서 관찰한 짧은 표본입니다.
- 원문 행 해시·종목·타입·가격/수량 문자열·호가 10단계·시장/수신 시각을 정규화 결과와 대조해 **1,081행 일치, 필드 불일치 0건**입니다. 이는 같은 공급자 원문의 저장/변환 대조이며 독립 거래소 원장이나 내 계좌 체결 결과와의 비교가 아닙니다.
- 실제 가격·수량·호가 원문을 저장소/PR에 게시하지 않습니다. [공개 요약](examples/actual-tick-validation-20261106.json)은 건수·품질 사유·해시만 포함합니다.

## 재발 방지 점검

루트에서 다음 명령은 Docker DB 메타데이터와 로컬 공개 GET만 읽습니다. 키·계좌정보·시세 값을 출력하지 않으며 스키마 적용·수집/주문 활성화는 하지 않습니다.

```powershell
python scripts/check_public_tick_readiness.py --from 2026-11-06T02:28:00Z --to 2026-11-06T02:30:00Z --output Back/spring-server/build-codex-tick-readiness/readiness-new.json
python -m unittest discover -s scripts -p test_public_tick_readiness.py -v
```

- `storageAndExportReady`: 025/026 테이블 존재와 두 공개 API 계약 확인. 성공일 때 종료 코드 0입니다. 원문 전체 무결성은 별도 tick 감사가 담당합니다.
- `persistedSampleAvailable`: 조회 범위에 체결·호가가 모두 존재하는지 확인. 빈 목록과 502를 혼동하지 않습니다.
- `continuousCollectionConfigurationDeclared`: 운영 플래그 선언 여부입니다. 양수 예산을 충분한 용량·브로커 한도/계약 확인으로 확대하지 않습니다. 이번에는 false와 운영 OFF가 정상적인 최종 상태입니다.
- 결과 파일은 배타 생성하며 기존 보고서를 덮어쓰지 않습니다. Windows SQL은 바이트 LF와 결과 형식을 검사합니다.

신규 점검 도구 **11개 테스트 통과**, 기존 틱 감사 **39개 테스트 통과**, 실제 1,081행 입력 대조를 확인했습니다. 이번에는 Java/Python 분석 런타임 소스를 변경하지 않았으므로 직전 전체 AI 1,118개 결과를 이번 전체 재실행 결과로 표시하지 않습니다.
