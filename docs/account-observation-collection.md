# R1 계좌 관찰 자동 수집과 상태 복구

기준일: 2026-11-03 · 상태: 백엔드와 Flutter 상태/재개 화면 구현. 로컬 Docker의 023·024 적용·API 응답을 확인했으며, 수집 활성화·실계좌 대조·Ubuntu 배포 검증은 후속입니다.

후속 [실제 읽기 관찰 점검](account-observation-live-validation.md)에서 보유/현금의 사용자 대조와 저장/이력을 확인했습니다. 지정일 주문 조회 실패로 전체 관찰은 PARTIAL로 남았으며 이 결과로 수집을 활성화하지 않았습니다. 아래 최초 개발 범위와 실환경 확인 범위를 구분합니다.

[계좌 관찰 저장](account-observation-history.md)을 서버에서 주기적으로 실행하는 기능입니다. 앱이 닫혀 있어도 서버 프로세스가 동작하고 설정이 활성화된 환경에서 관찰 이력을 쌓습니다. 관찰은 계속 `atomic=false`, `usableForTrading=false`이며 보유분·자본금·주문·예약·거래 원장에 자동 반영하지 않습니다. 실시간 시세 스트리밍은 R2에서 별도로 진행합니다.

## 1. 설정과 실행 조건

기본값은 다음과 같습니다. 이 예시는 이번 작업에서 실제 `.env`에 적용하지 않았습니다.

```dotenv
SAGOPALGO_ACCOUNT_OBSERVATION_COLLECTION_ENABLED=false
SAGOPALGO_ACCOUNT_OBSERVATION_COLLECTION_INTERVAL_SECONDS=900
```

활성화에는 수집 설정 ON, 개인용 모드 ON·유효한 로컬 사용자, KB 계좌 조회 ON, 연결/인증 설정이 모두 필요합니다. 키가 있다는 사실은 실제 권한·호출 성공을 증명하지 않습니다. OFF이면 수집 실행기를 등록하지 않고 자동 DB 예약·KB 호출도 하지 않습니다.

간격은 60~86400초이며 범위를 벗어나면 설정 바인딩이 실패합니다. 기본 900초는 시험용 수집 간격으로 공급자의 승인된 호출 한도를 뜻하지 않습니다. 활성화 전에 페이지·토큰·다른 계좌 조회/작업을 포함한 호출 예산을 확인합니다. 같은 계좌를 공유하는 서버에는 동일한 수집 설정을 사용합니다.

실행기는 서버 시작 60초 후 처음 확인하고, 확인 작업이 끝난 뒤 60초 간격으로 다시 확인합니다. 실제 다음 실행 가능 시각은 DB의 UTC 시각으로 판정하며, 정상 완료 후 `DB 완료 시각 + 설정 간격`입니다. 분 단위 확인 때문에 실제 실행에는 추가 지연이 있을 수 있고 과거 누락 주기를 몰아서 재생하지 않습니다.

실행기는 별도 단일 스레드를 소유하고 종료 시 닫습니다. 공용 TaskScheduler Bean으로 등록하지 않아 기존 알림·뉴스 스케줄러 선택을 바꾸지 않습니다. 장중·휴일 필터는 아직 없으므로 활성화하면 시간대/요일에 따른 제한 없이 due를 확인합니다. 주문 조회 날짜는 새 실행 예약 시 한국 날짜로 고정하며, 이전 날짜 요청을 복구할 때 바꾸지 않습니다.

## 2. 저장된 실행 상태

신규 [024 SQL](../Back/database/migrations/024_account_observation_collection.sql)은 `kb_account_observation_collectors`를 만듭니다. `(user_id,account_binding)` PK가 계좌 연결별 자동 수집을 구분하고, 실행 중 UUID·주문 조회일과 직전 종료 결과·차단 사유·다음 가능 시각을 보관합니다. 본문은 기존 023 관찰 테이블에만 저장합니다.

| 상태 | 의미 | 다음 확인의 동작 |
|---|---|---|
| `NOT_STARTED` | 현재 연결에 수집 상태 행이 없음 | 활성화 조건과 DB 예약을 통과하면 새 실행 |
| `IDLE` | 이전 실행 종료 확인, 다음 주기 대기 | DB due 조건을 만족할 때 한 요청만 예약 |
| `ACTIVE` | 실행 권한을 예약했지만 종료 대조가 끝나지 않음 | 기존 요청 ID의 저장 결과만 조회. 새 관찰을 실행하지 않음 |
| `PAUSED` | 관찰 종료는 확인됐지만 부분/실패/비활성/문제 결과로 중단 | 자동 반복하지 않음. 원인 확인 후 명시적 재개 필요 |
| `UNCONFIGURED` | 현재 연결의 설정 범위를 만들 수 없음 | 수집 상태 DB·KB를 조회하지 않고 설정 상태만 반환 |

`ACTIVE`는 실제 실행 중 또는 결과 미확정 상태입니다. 경과 시간만으로 프로세스 생존·실패·미접수를 판정하지 않습니다. 자동 만료/lease 강탈은 없습니다. 정책 OFF나 서버 재시작도 ACTIVE를 해제하지 않습니다.

실행 순서는 다음과 같습니다.

1. 사용자·연결 범위와 활성화 조건을 확인합니다.
2. 독립 트랜잭션에서 IDLE/due 행을 ACTIVE로 조건부 변경하고 새 UUID·조회일을 커밋합니다. 이 예약에 실패하면 KB를 호출하지 않습니다.
3. 예약에 성공한 요청만 기존 관찰 저장 서비스로 진입합니다. 그 서비스도 023 요청을 먼저 커밋하고 외부 호출 중 DB 트랜잭션·잠금을 유지하지 않습니다.
4. 실행을 예약한 연결과 실제 관찰 연결이 다르면 외부 조회 전에 차단합니다. 수집 중 연결 변경도 기존 관찰의 혼합 자료 차단을 유지합니다.
5. 정상 SUCCESS/COMPLETE·문제 없음 결과는 IDLE로 종료하고 다음 시각을 저장합니다. 부분/실패 결과는 PAUSED로 종료합니다.
6. 다른 실행기나 재시작은 ACTIVE의 기존 UUID만 읽습니다. 저장 상태가 COMPLETED/FAILED일 때만 조건부 완료를 기록하고, PENDING·404·저장소/무결성 오류는 그대로 남깁니다.

예약 후 023 관찰을 만들기 전에 종료됐거나, PENDING 상태로 프로세스가 중단된 경우도 ACTIVE를 보존합니다. 이 경우의 강제 해제 API는 제공하지 않습니다. 실행 프로세스·DB 기록·연결을 확인하는 운영 해결 절차는 후속이며 새로운 UUID로 자동 우회하지 않습니다.

실행 상태 확정이 실패해도 이미 저장된 관찰은 유지됩니다. 다음 확인이 그 결과를 읽어 수집 상태를 대조하므로 KB 관찰을 반복하지 않습니다. 같은 종료 결과를 여러 서버가 읽어도 요청 ID·조회일·ACTIVE 조건에 맞는 최초 UPDATE만 확정됩니다.

수동 새 관찰은 기존 API로 별도 실행할 수 있습니다. 자동 수집의 동일 주기 중복 차단은 모든 수동 계좌 조회를 묶는 전역 제한이 아니므로 호출 예산에 수동 조회도 포함합니다.

## 3. 상태 조회 API

`GET /api/v1/kb/accounts/primary/observations/collection`

현재 로컬 사용자·연결의 상태만 읽으며 관찰 생성·수집 예약·외부 조회·DB 쓰기는 하지 않습니다. 고정 경로는 기존 `/{requestId}` 상세와 공존합니다. 정상 응답은 공통 ApiResponse·no-store입니다.

| 응답 필드 | 의미 |
|---|---|
| `enabled`, `personalModeEnabled`, `accountEnabled`, `connectionConfigured` | 현재 설정. 실제 권한/접속 성공 표시가 아님 |
| `intervalSeconds`, `state` | 설정 간격·저장된 수집 상태 |
| `activeRequestId`, `activeOrderDate` | 종료 미확정 요청. 기존 상세로 조회 가능 |
| `lastRequestId`, `lastStorageState`, `lastSnapshotStatus` | 직전 종료 대조 기록 |
| `failureCode` | PAUSED의 고정 사유 |
| `nextDueAt`, `startedAt`, `completedAt` | DB UTC DATETIME(6) 기반 시각 |
| `readOnly=true`, `usableForTrading=false` | 증권사 읽기 관찰 범위. 거래 가능 판정 아님 |

설정 OFF에서도 이전 ACTIVE/PAUSED 기록은 그대로 보입니다. `enabled=true`나 과거 `nextDueAt`만으로 지금 수집 중이라고 판단하지 않습니다. 계좌 지문·계좌번호·키·SQL·사용자 ID는 응답에 포함하지 않습니다.

## 4. 중단 후 재개 API

`POST /api/v1/kb/accounts/primary/observations/collection/resume`

```json
{ "lastRequestId": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa" }
```

현재 PAUSED의 마지막 요청과 ID가 같고, 해당 관찰의 체크섬/계약·저장 종료·수집 메타데이터 일치가 확인돼야 합니다. ACTIVE·PENDING·기록 없음·다른 ID·손상 결과는 해제하지 않습니다. 성공하면 IDLE로 바꾸고 DB 현재 시각 + 간격 이후 새 주기를 허용합니다.

이 POST는 저장 기록 대조와 수집 상태 갱신만 수행합니다. 즉시 KB를 조회하거나 수집 설정을 ON으로 바꾸지 않습니다. 다음 주기는 새 UUID의 별도 관찰이며 중단된 관찰은 수정하지 않습니다. 재개 요청을 반복하면 이미 IDLE이므로 409가 될 수 있으며 상태 GET으로 결과를 확인합니다.

PAUSED 사유는 `SNAPSHOT_PARTIAL`, `SNAPSHOT_FAILED`, `SNAPSHOT_DISABLED`, `SNAPSHOT_UNUSABLE`, `OBSERVATION_FAILED`, `CONTEXT_CHANGED`입니다. 일부 성공 기록도 본문을 보존하되 자동 수집은 멈춥니다. 코드만으로 원인을 해결했다고 간주하지 않습니다.

두 API는 입력 오류 400, 상태/연결 충돌 409, 수집 저장소 오류 503 `OBSERVATION_COLLECTION_STORAGE_UNAVAILABLE`을 사용합니다. 관찰 원본을 대조할 때 기존 023 저장소/무결성 오류도 503으로 차단합니다. 저장소 예외 원문과 KB 응답은 로그·응답에 복사하지 않고 고정 오류 코드만 남깁니다.

## 5. 적용·검증·남은 범위

기존 설치는 [DB 백업·마이그레이션 절차](docker-architecture.md#기존-ubuntu-db의-kb-점검-이력-테이블)를 따라 023·024 적용과 백엔드 재배포를 확인합니다. 신규 schema.sql에도 024와 같은 정의를 추가했습니다. `.env.example`, application.yml, Compose는 새 설정을 기본 OFF로 전달합니다. 이번 작업은 실제 `.env`·운영 DB·실계좌·주문 스위치를 변경하지 않았습니다.

[기존 전용 MySQL 재현 절차](account-observation-history.md#5-격리-검증과-재현)와 같은 33317/마커/tmpfs 환경을 사용합니다. 새 통합 테스트가 실제 023·024를 적용하며 observer는 항상 mock입니다. 8개 독립 수집기·예약 전 커밋·cooldown·orphan/PENDING 보존·결과 갱신 롤백·부분 실패/재개·사용자/연결 격리·무결성·HTTP 경로를 검증합니다. 새 인스턴스/Mapper 재생성 시험이며 실제 운영 프로세스 종료/재시작을 수행한 것은 아닙니다.

상세 건수와 후속 로컬 적용 기록은 [진척도](development-progress.md)를 따릅니다. 위의 운영 미적용 설명은 최초 백엔드 개발 당시의 범위이며, 후속으로 로컬 Docker DB에 023·024를 적용하고 API 응답을 확인했습니다. Ubuntu 배포 검증·운영 활성화·권한/호출 예산·실계좌 대조·장기 복구, 일별 자산/입출금/체결 원장도 남아 있습니다.

## 6. Flutter 상태 확인과 명시적 재개

보유/설정 → `계좌 관찰 이력·비교` → `자동 관찰 수집`에서 확인합니다. [앱 동작·복구 조건](account-observation-ui.md#6-자동-수집-상태와-재개)을 따릅니다.

- 화면 진입·이력 새로고침·`수집 상태 확인`은 상태 GET만 실행합니다. 주기 폴링이나 자동 POST는 없습니다.
- 서버 수집 ON/OFF, 개인용 모드/계좌 조회/연결 구성, 간격, 실행 상태, 확인 시각과 DB 시작/종료/다음 실행 가능 시각을 표시합니다. 시각은 한국 시간이며 예정 시각이 실제 실행을 보장하지 않습니다.
- 진행/마지막 요청 ID에서 기존 관찰 상세로 이동할 수 있습니다. ACTIVE는 경과 시간과 무관하게 재개하지 않습니다.
- PAUSED와 종료 메타데이터·알려진 사유가 있을 때 `수집 재개`를 허용합니다. 최종 종료·무결성 대조와 현재 ID 일치 판정은 서버가 수행합니다. 서버 설정 OFF에서도 중단 기록을 재개할 수 있지만 설정은 계속 OFF입니다.
- 재개 POST는 한 번만 전송하며 진행 중 중복 클릭을 막습니다. 타임아웃·응답 유실·409·계약 오류 후에는 이전 PAUSED를 제거하고 상태 GET으로 확인해야 합니다. GET 확인 후 여전히 PAUSED이면 사용자가 명시적으로 다시 재개할 수 있으며 자동 재전송은 하지 않습니다.
- 상태 GET 실패도 이전 재개 대상을 제거합니다. 024 저장소 오류는 수집 패널에 안내하며 기존 이력 조회/수동 저장을 함께 차단하지 않습니다. 023 저장소 오류는 기존 저장/상세 API의 조건대로 처리합니다.

이 화면은 서버 환경변수 변경이나 즉시 수집 기능을 제공하지 않습니다. 앱 상태·이력은 확인 시점 기준이며 자동 화면 갱신은 후속입니다. 현재 로컬 수집 설정은 OFF로 유지했습니다.
