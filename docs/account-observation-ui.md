# R1 계좌 관찰 이력·상세·비교 화면

기준일: 2026-11-03 · 상태: Flutter 이력/비교 및 자동 수집 상태·재개 구현. 로컬 Docker의 023·024 적용·API 응답 확인과 실계좌 대조·사용자 앱 실행 확인은 구분합니다. 실계좌 대조와 Ubuntu 배포 검증은 후속입니다.

[관찰 저장·이력](account-observation-history.md)과 [관찰 비교](account-observation-comparison.md)를 Flutter Windows 앱에서 사용하도록 연결했습니다. 새 관찰 저장을 누를 때만 계좌 조회·저장을 요청하며, 화면 진입·새로고침·상세·비교·복구 확인은 GET으로 저장 이력만 읽습니다.

## 1. 사용 동선

1. **보유** 또는 **설정** 탭의 `계좌 관찰 이력·비교`를 엽니다.
2. 주문 조회일을 `YYYYMMDD`로 입력하고 `새 관찰 저장`을 누릅니다. 기본 날짜는 한국 날짜이며 보유·잔고는 요청 당시 상태입니다. 과거 주문 날짜를 선택한다고 과거 잔고를 조회하지 않습니다.
3. 저장 결과를 받으면 상세 화면을 엽니다. 저장 상태와 실제 관찰 결과 상태를 별도로 표시합니다. PENDING은 결과 대기이며 실행 중/중단 여부를 확정하지 않습니다.
4. 상세에서 보유·결제기준 잔고·체결기준 잔고·지정일 주문을 펼쳐 범위·수신 시각·페이지/행 수·완전성·문제·요약·행 필드를 확인합니다.
5. 이력 화면에서 이전·이후 관찰을 선택해 비교합니다. 같은 기록을 선택하면 비교 버튼이 비활성화됩니다. 순서를 바꿀 수 있으며 시간 역전·범위 차이 등은 서버가 판정합니다.

이력은 최근 20건부터 서버 커서로 더 읽습니다. 페이지 사이 중복 항목은 요청 ID로 합치며 다음 페이지 오류가 나도 기존 항목과 재시도 버튼을 유지합니다. 전체 새로고침은 선택과 이전 목록을 비우고 현재 연결 범위를 다시 읽습니다.

행 상세는 처음 25개를 렌더링하고 `저장된 행 더 보기`로 펼칩니다. 저장된 내용을 화면에 더 표시하는 동작으로 KB를 재조회하지 않습니다. 가변 폭/긴 숫자는 줄바꿈하고 기존 앱의 밝은/어두운 테마를 사용합니다.

## 2. 응답 유실과 로컬 복구

저장 요청은 다음 순서입니다.

1. 실제 날짜를 검사하고 진행 중인 중복 클릭을 차단합니다.
2. 보안 난수로 UUID v4를 만들고 요청 ID·주문 조회일을 로컬 파일에 START로 기록·flush합니다. 기존 기록을 읽을 수 없거나 새 기록 쓰기에 실패하면 POST를 보내지 않습니다.
3. UUID·조회일만 담은 POST를 한 번 보냅니다. HTTP 요청은 60초 제한이며 자동 재시도하지 않습니다. 타임아웃이 서버의 실행/저장을 취소했다는 뜻은 아닙니다.
4. 같은 ID·조회일의 유효한 응답을 받았고 저장 상태가 COMPLETED/FAILED이면 로컬에 COMPLETE를 추가합니다. PENDING은 확인 대상으로 남깁니다.
5. 통신 오류·404·503·형식/계약 오류·요청 불일치에는 미확인 요청을 남깁니다. 화면을 다시 열거나 Repository를 재생성해도 복구 목록을 읽을 수 있습니다.

미확인 항목의 `저장 상태 확인`과 상세 화면 새로고침은 **같은 요청 ID의 GET**입니다. 404라도 POST로 대체하지 않습니다. 기록 없음·서버 이전 버전·연결 변경을 클라이언트가 구분해 접수 여부를 추측하지 않습니다. 필요하면 서버/연결/원래 요청을 확인한 뒤 별도의 새 관찰을 명시적으로 실행합니다. 새 관찰은 이전 요청의 재시도/완료가 아닙니다.

Windows의 파일 위치는 `%LOCALAPPDATA%\SagoPalgo\account-observation-requests.jsonl`입니다. 다른 로컬 개발 환경은 HOME 아래 SagoPalgo를 사용하며 영속 위치가 없으면 저장을 차단합니다. 임시/무기록 저장소로 자동 대체하지 않습니다.

- 로컬 기록에는 서버 주소·앱 로컬 사용자 식별 범위, 요청 UUID·조회일·START/COMPLETE만 있습니다. 금액·잔고·계좌번호·KB 키·토큰·관찰 본문은 기록하지 않습니다. 서버 URL의 인증/쿼리/fragment도 범위 값에서 제거합니다.
- 서버 주소·로컬 사용자별로 목록을 분리합니다. 이것은 클라이언트 복구 범위이며 KB 계좌 식별/접근 권한은 서버의 LocalUserContext·연결 HMAC 필터가 담당합니다.
- 같은 서버의 KB 키/계좌 설정이 변경돼도 미확인 요청을 임의 삭제·새 계좌로 승계하지 않습니다. 서버 404/409와 기존 요청 ID를 유지합니다.
- COMPLETE는 로컬 확인 기록이며 서버 요청을 취소·종결·삭제하지 않습니다. 파일은 추가 기록 방식으로 재생하며 자동 만료·압축·이전·수동 추적 종료 기능은 후속입니다.
- 복구 파일이 손상됐으면 새 저장 버튼을 차단하고 오류를 표시합니다. 저장 이력 GET은 계속 사용할 수 있습니다. 기존 ID를 잃을 수 있으므로 파일을 자동 삭제하거나 초기화하지 않습니다.

## 3. 표시 계약

금액·수량·변화량은 서버 문자열을 그대로 표시합니다. double 변환·단위 환산·P6 대체·반올림·누락의 0 치환을 하지 않습니다. 문자열이어야 할 값이 JSON 숫자로 오면 계약 오류로 처리합니다.

| 표시 | 의미 |
|---|---|
| `0` | 실제 전달된 0 |
| `값 미제공` | 명시적 null |
| `필드 없음` | 비교에서 해당 필드 자체가 없음 |
| `변화량: 산정하지 않음` | 서버가 변화량을 제공하지 않음 |
| `이전/이후 관찰에서만 확인` | 한쪽에서만 보인 행. 매수·매도·주문 종결 판정 아님 |

상세는 UTC 서버 시각을 한국 시각으로 표시하고, 공급자 처리 시각은 시간대를 추정하지 않고 원문과 미확인 표시를 유지합니다. 정정/취소 구분 등 공급자 코드는 원래 필드를 표시하며 완료 의미를 추가 해석하지 않습니다.

버전·Provider·읽기 전용/거래 불가 플래그·4개 구간 순서·요청 ID·조회 날짜·관찰 ID/상태를 검증합니다. 비교는 반환된 이전/이후 ID를 확인하며 차단 구간에 차이 목록이 들어오면 거부합니다. 알 수 없는/손상된 응답을 빈 계좌나 성공 결과로 만들지 않습니다.

오류 화면은 고정 한국어 메시지를 사용하며 외부 응답 본문·SQL·예외 전문을 복사하지 않습니다. 서버 저장소 오류에는 023 적용 상태 확인, 404에는 배포·연결·요청 확인, 409에는 현재 연결의 이력 새로고침을 안내합니다.

## 5. 배포와 남은 일

- 서버에 [023 테이블](../Back/database/migrations/023_account_observation_history.sql)과 저장·비교 API가 배포돼 있어야 합니다. 이번 작업은 서버/DB/키/주문 스위치를 변경하거나 실제 KB를 호출하지 않았습니다.
- Flutter UI 변경이므로 새 Windows 앱 빌드가 필요합니다. EXE와 같은 빌드 폴더의 DLL·data를 함께 사용합니다. 이번 로컬 빌드가 사용자 PC 배포/실행 확인을 뜻하지 않습니다.
- 실제 KB 조회와 잔고·수량 대조, 운영 복구 확인은 남아 있습니다. 이 화면은 수집 설정 변경·주문·체결 원장·기간 성과를 제공하지 않습니다.

## 6. 자동 수집 상태와 재개

`자동 관찰 수집` 패널은 동일 Repository의 `collectionStatus()`와 `resumeCollection(lastRequestId)`로 기존 상태/재개 API를 사용합니다. [패널 구현](../Front/app_version/lib/screens/observation_collection_panel.dart)은 이력 조회와 오류를 분리하며, `test/observation_collection_test.dart`에서 실제 Repository와 모의 HTTP를 연결해 검증합니다.

1. 화면 진입·이력 새로고침·`수집 상태 확인`은 GET입니다. 확인 시각을 표시하며 자동 폴링·수집 활성화는 없습니다.
2. 서버 설정 ON/OFF와 실행 상태를 별도로 표시합니다. NOT_STARTED/IDLE/ACTIVE/PAUSED/UNCONFIGURED, 간격, 마지막 결과·사유, 진행/직전 요청 ID와 한국 시간의 실행 기록을 확인할 수 있습니다. 연결 구성은 실제 KB 권한/호출 성공을 뜻하지 않습니다.
3. `진행 관찰 상세`·`마지막 관찰 상세`는 기존 요청 ID의 상세 GET을 엽니다. ACTIVE는 실행 중 또는 종료 미확정이며 시간 경과로 해제하지 않습니다.
4. PAUSED·종료 결과·알려진 중단 사유가 있어야 재개 버튼을 활성화합니다. PENDING/미확인 메타데이터는 차단하며 최종 현재 ID·종료·무결성 검증은 서버가 수행합니다.
5. `수집 재개`는 마지막 요청 ID를 한 번만 POST합니다. 성공 시 IDLE·다음 실행 가능 시각을 표시하며 즉시 KB 조회나 환경 설정 ON을 하지 않습니다. 설정 OFF인 경우에도 OFF가 유지된다는 안내를 표시합니다.
6. 재개 응답을 확인하지 못하면 이전 상태를 제거하고 GET 상태 확인을 안내합니다. 자동 POST 재시도는 없습니다. 화면 재진입도 GET만 실행합니다. 상태 GET 실패 역시 이전 PAUSED로 재개할 수 없도록 처리합니다.

금액·수량 처리와 수동 저장의 로컬 UUID 복구 정책은 기존 계약을 따릅니다. 재개는 기존 서버 요청 ID를 사용하며 수동 저장의 새 UUID나 START 기록을 만들지 않습니다. 024 미적용/저장소 오류는 패널에 고정 문구로 안내하고 외부 오류 원문을 노출하지 않습니다.
