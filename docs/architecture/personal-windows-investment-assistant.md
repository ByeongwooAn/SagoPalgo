## 방향성

SagoPalgo는 Flutter Windows 기반의 `.exe` 프로그램으로 실행합니다. 사용자는 본인 PC에서 본인 증권사 API Key를 등록하고, 계좌 조회, 보유 종목 분석, 시장 데이터 조회, 뉴스/공시 기반 AI 분석, 알림 기능을 개인 용도로 사용합니다.

핵심 원칙은 다음과 같습니다.

- 실제 계좌 조회, 주문, 체결 같은 금융 업무는 KB증권 Open API만 사용합니다.
- KIS와 Toss Open API는 계좌나 주문 연동 없이 주식 정보와 시장 데이터 조회 용도로만 사용합니다.
- 앱은 로그인 화면 없이 바로 로컬 개인 프로필로 진입합니다.
- 기본 시세 Provider 하나를 우선 사용하고, 장애나 데이터 부족이 있을 때만 fallback Provider를 사용합니다.
- AI 분석기는 증권사별 응답 구조를 직접 알지 못하고, 정규화된 내부 데이터 모델만 사용합니다.
- 자동매매는 초기 구현 대상이 아니며, 모의매매와 승인형 주문을 거친 뒤 제한적으로 도입합니다.

## API 역할 분리

| 영역 | 메인 | 보조 | 비고 |
|---|---|---|---|
| 계좌 조회 | KB증권 | 없음 | 실제 계좌가 KB이므로 KB 고정 |
| 보유 주식 분석 | KB증권 | 없음 | 보유 단가, 수익률, 비중 기준 |
| 주문/매수/매도 | KB증권 | 없음 | 추후 구현 시에도 KB만 사용 |
| 국내 현재가 | KB 또는 Toss | KIS | 하나를 기본값으로 쓰고 나머지는 fallback |
| 해외 현재가 | KB/KIS/Toss 중 선택 | 나머지 | 지원 범위와 안정성 확인 후 결정 |
| 종목 정보 | Toss/KIS | KB | 종목명, 시장, 경고, 랭킹 등 |
| 뉴스 | Naver News API 등 | 기타 뉴스 API | 원문 저장보다 링크/요약 중심 |
| 공시 | OpenDART | 없음 | 국내 기업 분석에 중요 |
| AI 분석 | OpenAI API 또는 로컬 LLM | 없음 | 개인 설정으로 선택 가능 |

같은 종목의 현재가는 원칙적으로 하나의 시장 가격입니다. 따라서 세 증권사 API에서 같은 가격을 매번 모두 호출해 평균을 내는 방식은 기본 전략으로 사용하지 않습니다. 여러 Provider는 가격 자체를 합치기보다 장애 대응, 데이터 품질 검증, Provider별 부가 데이터 보강 용도로 사용합니다.

## 데이터 흐름

```text
1. KB API에서 내 계좌와 보유종목을 조회합니다.
2. Market Data Provider에서 현재가, 캔들, 거래량, 시장 지표를 조회합니다.
3. News/OpenDART Provider에서 뉴스와 공시를 수집합니다.
4. Provider별 응답을 내부 표준 모델로 정규화합니다.
5. AI Analysis Service가 종목별/계좌별 리포트를 생성합니다.
6. Alert Service가 가격, 뉴스, 공시, AI 신호 조건을 평가합니다.
7. Flutter Windows 위젯, 대시보드, Windows 알림으로 결과를 표시합니다.
8. 추후 주문 기능은 KB Order Safety Service를 반드시 통과합니다.
```

## 자동매매 안전장치

자동매매는 초기 구현 대상이 아닙니다. 추후 구현하더라도 다음 단계를 순서대로 통과해야 합니다.

1. 모의매매
2. 주문 전 확인 팝업
3. 수동 승인 주문
4. 제한적 자동매매

필수 안전장치:

- 기본값 자동매매 OFF
- 실전투자보다 모의투자 우선
- 1일 최대 주문 횟수 제한
- 1회 최대 주문 금액 제한
- 종목별 최대 보유 비중 제한
- 손실 한도 도달 시 자동 중지
- 모든 판단, 조건, 주문 요청, 응답 로그 저장
- AI 단독 주문 금지 옵션

## 기존 11단계 개발 로드맵과 구현 이력

### 1단계: Flutter Windows 전환

- 상태: 완료
- Windows 빌드 활성화 상태 확인
- `.exe` 실행 확인
- 기본 창 제목과 앱 메타데이터를 SagoPalgo로 정리
- 기존 모바일 UI가 데스크톱 화면에서 깨지지 않도록 1차 점검
- Windows 빌드 환경에는 Visual Studio의 `Desktop development with C++`, `C++ CMake tools for Windows`, `Windows 10 SDK`가 필요합니다.

### 2단계: 개인용 설정 구조 정리

- 상태: 완료
- Google/Naver 로그인 화면 제거
- 개인용 로컬 사용자 세션으로 즉시 대시보드 진입
- 백엔드에서 로그인/JWT/OAuth 코드 제거
- 백엔드 개인용 모드에서 로컬 사용자 ID 주입
- `users` 테이블은 다중 회원이 아니라 로컬 소유자 호환 테이블로 유지
- Windows Credential Manager 기반 앱 잠금 PIN 등록·변경·삭제 구현 완료
- 기존 `SAGOPALGO_APP_LOCK_PIN`의 1회 자동 이전 구현 완료
- KB/KIS/Toss Provider 설정 분리
- 증권사 연동 상태 조회 API 추가
- Flutter Windows 설정 탭 추가
- 주문 권한 기본 OFF
- Windows 로컬 PIN은 Credential Manager, Ubuntu Provider 비밀값은 서버 루트 `.env`로 분리

### 3단계: KB 계좌 연동

- 상태: 완료

### 4단계: 시장 데이터 Provider 정리

- 상태: 완료

- 추천 본문, 점수 근거, 분석 요청·응답 원문 저장 구현 완료
- 추천 분석 실행, 목록, 상세 API 구현 완료
- AI 서버 장애 시 기존 규칙 엔진 fallback과 대시보드 최신 저장 추천 연동 완료
- Flutter 추천 이력 페이지 조회, 상세 화면, 보유 종목 수동 재분석 구현 완료
- 관심 종목 직접 분석과 등록 보유 종목의 매입 원금 비중 신호 구현 완료

- 보유 종목의 AI 응답이 손절·익절 임계값 또는 자본금 비중 한도와 모순되면 규칙 분석으로 대체
- KB 결제기준 잔고의 응답 평가비중과 보유주식 조회의 계산 비중을 출처별로 구분해 현재 응답 항목을 확인하는 읽기 전용 화면 구현 완료
- KB 결제기준 잔고의 보고 건수와 현재 표시 건수 차이를 읽기 전용 경고로 표시. 건수 일치도 조회 완전성을 입증하지 않음
- KB 실계좌 전체의 실시간 평가 비중 검증과 분석 장기 운영 검증은 다음 확장 범위

- KB `SSQM2341` 읽기 전용 주문 이력 조회와 주문번호별 페이지 대조 API 구현 완료 (실계좌 응답 수동 검증 필요)
- 승인별 단일 제출 가드 영속화, 원자적 1회 예약, 불명확 상태 기록과 조회 API 구현 완료. D 묶음에서 독립 트랜잭션으로 전송 전 커밋하고 미확정 전송의 신규 승인 우회를 차단
- 알려진 주문번호로 `RESERVED`·`UNCERTAIN` 승인과 KB 조회 행을 함께 검토하고 조회 요약을 저장하는 API 구현 완료 (자동 접수 판정 없음)
- 주문번호가 없는 불명확 응답의 날짜별 KB 이력 최대 10페이지·200행 수동 검토와 요약 감사 기록 API 구현 완료 (자동 동일 주문 판정 없음)
- 실주문 별도 기본 OFF 스위치, 운영 IP/MAC·공식 URL·인증 경로·016 저장소 점검 API와 Flutter 설정 화면 구현 완료
- 승인 확인 후 90초의 제출 예약 기한과 원자적 만료 차단 구현 완료. 기존 기한 없는 `READY` 기록은 `LEGACY_REVIEW`로 이관
- KB 주문 이력의 수동 읽기 전용 권한 점검 결과를 민감정보 없이 저장하고, 마지막 결과·시각을 설정 화면 재진입 시 표시 (실주문 가능 판정에는 미사용)
- 수동 읽기 전용 점검의 최근 10건을 요청 시에만 펼쳐 확인 (사용자별 이력, KB 재호출·주문 상태 변경 없음)
- D 제한 범위: 정규장 KRX 지정가 수동 전송, 감사 기록, 체결 수동 조회, 당일 전량 미체결 신규 주문의 한 차례 지정가 인하/전부 취소와 별도 재확인 구현. [구현 범위·배포·제약](../orders/kb-manual-orders.md) 참고
- 운영 DB 016 적용은 사용자 확인 완료. 실제 격리 MySQL 경쟁 실행은 후속 검증 완료. 017~021 운영 적용·새 백엔드/EXE 배포와 실계좌 권한/응답 대조·별도 승인된 제한 주문 검증은 남음
- UNKNOWN 신규 주문의 알려진 KB 번호를 전량 체결 대조 후 사용자 확정하는 제한 복구 구현. 최초 결과·제출 가드 보존, 90초 토큰과 재조회, 별도 감사 기록 및 신규 제출 차단 집계 연결

- UNKNOWN 잔량/변경 주문의 잠금 유지 관찰과 원주문 추가 조회 구현. 공식 공개 JSON·Excel·전체 샘플·GitHub에서 변경 완료 코드값 근거는 찾지 못했으며 실제 차단 해제로 연결하지 않음
- 가상 증권사의 소유권·전송 종료·전량 체결/명시적 취소·대체를 확인하는 시뮬레이터 전용 종결 구현. UNKNOWN·자원·전송 횟수를 보존하고 별도 동의/감사 저장 후 해당 가상 차단만 제외. 실제 수동 주문에는 적용하지 않음. [범위·출처·확인 절차](../orders/order-completion-evidence.md)
- 당일 전량 미체결 신규 주문의 한 차례 지정가 인하/제한적 증액 구현. 매수 증액은 기존 예약금 재사용 없이 새 전체 금액 이상의 현재 주문가능현금과 명시적 검사 성공 필요. 준비/제출 직전 재검증·이전/새 가격과 별도 동의·가상 정산/경쟁 실행 검증은 [지정가 변경 문서](../orders/order-price-amendment.md) 참고
- 이후 작업: KB 실제 완료 계약 확보와 UNKNOWN 잔량/변경 종결, 종료 증거 없는 SENDING 종결, 예약금 재사용 증액·추가 정정/수량 변경 범위 및 실환경 검증. 시뮬레이터 종결을 10단계 전체 완료로 계산하지 않음
- 4·5번 후속: 시뮬레이터의 정상 접수/잔량·자식 배분 근거로 추가 정정·일부 정정/취소·부분체결 뒤 잔량 변경과 선택 예약금 재사용을 구현. 같은 잔량 스냅샷의 중복 소비를 막고 거절/미확정 가드는 유지. 실제 KB는 계보·잔량·주문별 예약금 계약 미확보로 기존 제한을 유지하며 미지원 quantity/reuseReservation을 명시적으로 거절. [구현/미완료 구분·검증](../orders/order-partial-changes.md)

### 11단계: 제한적 자동매매

10단계의 후속 기능 검증을 위해 별도 [주문 시뮬레이터](../orders/order-simulation.md)를 추가했습니다. 공통 주문 코어와 가상 계좌/실패 시나리오를 사용하며 기존 9단계 PAPER 매매와 분리됩니다. 시뮬레이터 구현은 11단계 자동매매 완료를 뜻하지 않습니다.

- 상태: 미착수
- 기본 OFF
- 검증된 전략만 허용
- 손실 한도 도달 시 자동 중지
- 조건부 승인형 자동화부터 시작

## MVP 범위

1차 MVP는 다음 기능을 목표로 합니다.

- Flutter Windows 실행
- KB 계좌 조회
- 보유 주식 목록
- 현재가 갱신
- 관심종목
- 뉴스/공시 링크
- AI 보유종목 분석
- 가격/뉴스/포트폴리오 리스크 알림

D(10) 후속으로 [SENDING 저장 결과 복구](../orders/order-dispatch-recovery.md)를 구현했습니다. 019의 RESERVED/DISPATCHING/RETURNED 기록과 실주문·시뮬레이터 공통 결과 검증을 사용하고 종료 결과가 남은 SENDING만 사용자 확인으로 복구합니다. 신규 전송·기존 승인 가드 해제는 없으며 UNKNOWN과 종료 증거 없는 기록은 차단합니다. 운영 017/018/019 및 실계좌 검증은 별도이며 11단계는 미착수입니다.

D(10)에 [종료 결과 없는 SENDING 수동 진단](../orders/sending-manual-diagnostics.md)을 추가했습니다. 일치·빈 결과를 포함한 관찰을 별도 020/시뮬레이터 JSON에 기록하며 재전송·상태 변경·가드 해제는 하지 않습니다. 다음 개발 범위는 UNKNOWN 부분체결/변경 주문 대조와 추가 변경이며, SENDING 종결/해제와 실제 계좌 검증은 별도로 남아 있습니다.

D(10)에 [UNKNOWN 미체결·부분체결·정정/취소 대조 관찰](../orders/unknown-order-reviews.md)을 추가했습니다. 021 준비/이력과 90초 재조회 확인을 사용하며 UNKNOWN·가드·차단은 보존합니다. 공식 변경 구분의 값별 의미를 확인하기 전에는 성공/취소 완료로 추정하지 않습니다. 다음은 변경 완료 판정·잔량/변경/SENDING 종결과 추가 정정·실계좌 검증이며 자동매매는 미착수입니다.

D(10)에 [전송 시작 전 예약 중단](../orders/reserved-order-abort.md)을 추가했습니다. 022의 ABORTED 단계·별도 감사와 전송 시작 조건부 갱신으로 지연된 전송을 차단합니다. 원본 SENDING·제출/변경 가드를 유지하고 증명이 일치하는 명령만 pending에서 제외합니다. 메인 PC 구동 테스트는 사용자 확인을 반영했고 022 배포·새 화면 대조는 남습니다. 실제 KB 변경 완료 계약/UNKNOWN·DISPATCHING 종결·추가 변경·제한 주문/장기 운영 검증 후 11단계 착수 여부를 결정합니다.

2026-11-02 D(10)의 [실제 첫 일부 수량 정정·취소](../orders/manual-partial-order-changes.md)를 추가했습니다. 당일 전량 미체결 NEW의 첫 변경만 선택 수량으로 요청하고 원본·변경 가드를 보존합니다. 메인 PC 022 적용·새 백엔드 반영/Windows 빌드·DB/GET 점검은 완료했으며, 실제 완료 계약/UNKNOWN·시작 이후 SENDING 종결·추가 정정/예약금 재사용·실거래 검증과 11단계 자동매매는 남습니다.
