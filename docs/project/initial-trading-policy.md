# R0 초기 운용·측정 기준과 실행 계획

기준일: 2026-11-02 · 상태: 설계·시험용 초안. 사용자 실운용 한도·시장·시간 설정을 확정하거나 코드/운영 환경에 적용한 문서가 아닙니다.

[최신 로드맵](realtime-trading-roadmap.md)의 단기 착수 범위를 [API 지원표](../contracts/trading-api-contract-matrix.md)와 [KB 보류 목록](../contracts/kb-contract-blockers.md)에 연결합니다. 시간 구분은 일정 약속이 아니라 개발 순서입니다. 전체 R0는 외부 계약·계정별 권한·운용 값이 확정될 때 완료합니다.

## 1. 단기·중기·최종 목표

| 구분 | 목표 | 주요 작업 | 완료 증거 |
|---|---|---|---|
| 단기 · R0 및 R1~R3 착수 준비 | 답변 대기와 독립 개발의 경계 확정 | API 지원표·보류/재개 조건·초기 정책·이벤트/계좌 기록 설계 | 공식/코드/실환경의 구분, 구현 가능한 작은 작업 목록 |
| 중기 · R1~R7 및 R10 기본 | 실시간 관찰과 검증된 모의 자동 운용 | 계좌 동기화·시세/사건 저장·시장 후보·학습/재현·모의 자금 배분 | 실제 데이터 품질/지연·재연결, 비용 포함 독립 평가, 모의 원장 일치 |
| 최종 · R8 및 R10 | 한도 내 온주 실계좌 자동매매와 기간별 성과 | 실제 계약에 맞는 주문·체결·중지/복구, 온주 원장과 일·주·월·연 성과 | 필수 계약 해소·검증된 제한 실거래·원장 대조·운영 확인 |

소수점·추가 상품과 공급자 확장은 [보류 작업](deferred-work.md)에서 관리합니다.

## 2. 초기 범위 제안과 확정이 필요한 값

개발 복잡도를 줄이기 위한 초기 제안은 한 계좌·국내 현물·단일 거래소·온주·읽기/모의 우선입니다. 이 제한을 최종 목표의 국내외/소수점 지원 삭제로 해석하지 않습니다.

| 항목 | 설계·시험 기준 | 확정 전 적용 제한 |
|---|---|---|
| 계좌/종목 관리 | 외부 KB 조회와 앱 수동 등록·전략 관리분을 구분 | 기존 보유를 전략이 자동 매도할 대상으로 임의 편입하지 않음 |
| 거래 상품/시장 | 첫 연결은 국내 현물·한 거래소, KB 계좌/주문과 KIS 시세의 식별자 일치 | 실제 거래소·세션을 확정하기 전 통합 시세로 특정 시장 주문 판정 금지 |
| 관심/후보 | 자체 관심목록 우선, 보유종목 관리와 시장 후보 구독을 분리 | KB 관심목록/실시간 지원을 추정하지 않음 |
| 전략 주기·보유 시간 | 화면 갱신·판단 간격·최대 보유 시간·재진입 간격을 별도 값으로 설계 | ‘단타’라는 표현만으로 임의 초단위/당일 청산 정책을 운영에 적용하지 않음 |
| 수량 정밀도 | 계좌 조회의 원본 수량을 처음부터 보존 | 자동 주문은 국내 대상 시장 온주 범위에서 검증 |
| 자금 배분 | 실제 주문가능금액·기존 보유·미체결·비용을 함께 반영 | 모의 자본금/사용자 입력값을 실잔고로 대체하지 않음 |
| 손실·노출 한도 | 거래당/일간/종목/업종/총 노출·주문 횟수·가격 이탈을 분리 | 금액/비율 수치가 정해지지 않은 전략을 실운영 활성화하지 않음 |
| 중지/재개 | 신규 진입 중지·미체결 취소·보유 청산·재개를 독립 명령으로 설계 | 앱 종료·재접속·서버 재시작만으로 전략을 자동 활성화하지 않음 |

## 3. 데이터 계약에서 먼저 고정할 항목

R1~R3 설계에 공통으로 사용할 항목입니다. 최종 필드 이름·DB 구조는 다음 구현에서 정하고 API 호환성을 검토합니다.

- **식별자:** Provider, 계좌 지문(외부 노출 금지), 시장/거래소, 종목, 통화, 세션, 외부 이벤트/주문 식별자.
- **시각:** 시장/공개 시각과 서버 수신 시각을 분리합니다. 날짜만 제공된 자료는 `DATE` 정밀도로 남기고 임의 자정·초 단위 시각을 생성하지 않습니다. 저장 시간대·거래일 경계를 명시합니다.
- **수치:** 금액·수량은 십진 값과 단위를 보존합니다. 소수점 원본을 기존 4자리 주문/보유 수량으로 조용히 반올림하지 않습니다.
- **품질:** 추정/확정·정정 버전·지연 도착·중복·누락·출처 변경·실제 시세/fallback을 구분합니다.
- **조회 완전성:** 요청 범위·첫/마지막 페이지·다음키·종료 근거·부분 오류·상한 잘림을 기록합니다. ‘일부 성공’과 ‘전체 완료’를 분리합니다.
- **멱등성과 계보:** 같은 자료 재수신/재시작의 중복 반영을 막고, 주문/변경 식별자는 공식 계약이 확인된 관계만 연결합니다. 내부 관찰 ID로 실제 접수/체결을 추정하지 않습니다.

## 4. 지연·품질·호출량 측정 계획

### 4.1 관측 지점

| 지표 | 측정 기준 | 검증할 상황 |
|---|---|---|
| 시세 수신 지연 | 신뢰 가능한 시장 시각 → 서버 수신 | 거래소/시계 오차·장중 부하·지연 자료 |
| 서버 전달/화면 지연 | 서버 수신 → 이벤트 발행 → 앱 수신 → 표시 | 구독 수 증가·화면 재진입·느린 앱 |
| 판단 지연 | 유효 이벤트/봉/사건 도착 → 특징 완료 → 예측 완료 | 모델 교체·다중 후보·학습 작업 병행 |
| 사건 수집 지연 | 원 공급자의 공개 시각 → 수신/저장 | 날짜만 있는 자료는 초 단위 지표에서 제외, 정정·지연 도착 별도 |
| 재연결 품질 | 단절 시작 → 재구독 → 스냅샷 대조 완료 | 누락 범위·중복 처리·오래된 캐시 |
| 조회 완전성 | 페이지/행 수·종료 근거·잘림·최종 완료 시각 | 페이지 상한·반복 다음키·부분 실패 |
| 계좌 대조 | KB 현금/보유/미체결과 내부 관찰/예약 차이 | 수동 거래·부분 체결·조회 시점 불일치 |
| 호출/구독 예산 | Provider·키·API별 요청량/응답 제한·활성 구독 | 공유 키의 다른 작업·재시도·페이지·재접속 급증 |

p50/p95·최댓값·오류율·표본 수·시간대·후보/구독 수·네트워크 환경을 함께 남깁니다. 서버 처리 지연과 외부 공급 지연을 합쳐 모델 성능으로 보고하지 않습니다. 실제 주문의 송신→접수→체결→조회 반영 지연은 R8의 별도 승인된 검증에서 측정합니다.

### 4.2 처음 수행할 격리 시험 프로필

실제 API 권한·요금·한도와 무관한 로컬 재생 시험입니다. 아래 값은 금융 한도나 실시간 공급 보장치가 아닙니다.

- 1·20·50개 종목을 대상으로 중복/역전·부분 실패와 연결 단절을 재생합니다.
- 같은 입력을 반복/재시작해 저장 중복·평가 합계·봉 결과가 같아야 합니다.
- 각 시험은 최소 10분 재생과 3회 단절/재연결을 포함하고 입력량·p50/p95·누락/중복 수를 기록합니다.
- 잘못된 시각·음수/잘못된 가격·지원하지 않는 거래소·낡은 시세/fallback을 별도로 주입합니다. 분석/신규 주문용 입력에서 제외되는지 검증합니다.
- 실제 계좌·주문 호출과 주문 상태 변경 없이 실행할 수 있어야 합니다. 이 시험만으로 외부 권한·실시간 공급 품질을 통과 처리하지 않습니다.

자료를 확보한 뒤 전략 유효 시간과 수집 결과를 바탕으로 허용 지연·시세 만료 시간·구독 상한을 확정합니다. 측정 전 임의 지연 목표를 운영 기준으로 확정하지 않습니다.

### 4.3 뉴스 호출 예산 예시

[NAVER 공식 검색 규격](https://api.ncloud-docs.com/docs/naver-api-hub-search-news)은 하루 25,000회와 검색 페이지 범위를 안내합니다. 예를 들어 20개 종목을 390분 동안 분당 한 번·한 페이지씩 조회하면 `20 × 390 = 7,800회`입니다. **390분은 예산 산술 예시이며 실제 거래시간 확정값이 아닙니다.** 페이지·재시도·다른 작업·다른 시장 수집을 더해야 하고 키/상품의 실제 적용 한도는 별도로 확인합니다.

모든 종목을 같은 주기로 무조건 조회하지 않고 시장 사건 탐색과 후보 상세 조회의 예산을 나눕니다. 검색 상한 밖의 자료는 더 빠르게 폴링한다고 복구된다고 가정하지 않습니다. OpenDART와 KIS/KB도 각 계약의 제한 단위·키/계좌 공유 범위가 확인되기 전 같은 수치를 복사하지 않습니다.

## 5. 실운영 이전에 확정할 정책

| 정책 묶음 | 확정할 값 | 확인 시점 |
|---|---|---|
| 대상 | 계좌·시장·세션·상품·기존 보유 관리 동의 범위 | 실제 읽기 연결/전략 편입 전 |
| 시간 | 판단 간격·신호 유효기한·보유 시간·장 마감/거래정지 정책 | 전략 재현·실시간 모의 전 |
| 자금 | 운용 자금·비용 여유금·종목/업종/총 비중·예약 대조 | 자금 배분 모의 전 |
| 손실 | 거래당/일간 손실 기준, 실현/평가 포함 범위, 중지 후 처리 | 모의 정책 비교 후 실운영 활성화 전 |
| 데이터 | 만료 시간·호출/구독 예산·정정/결측 처리·보존 기간 | 실제 수집 확대 전 |
| 운영 | 긴급 중지·취소/청산 분리·재시작 대조·재개 조건 | 자동 주문 검증 전 |

기존 앱의 1회 주문금액/가격 이탈 기본값은 현재 수동 주문의 구현값입니다. 새 AI 자동매매의 손실·자금 한도가 확정된 것으로 사용하지 않습니다.

## 6. 답변 대기 중의 실행 순서

| 작업 묶음 | 브랜치 예시 | 지금 가능한 구현 | 착수/완료 조건 | 계속 보류할 동작 |
|---|---|---|---|---|
| 다음 1: R1 계좌 관찰 계약 | `feature/account-snapshot-contract` | 계좌 스냅샷·완전성·정밀도·출처/시각 모델과 조회 어댑터 연결, 격리 테스트 | A01/A02/A04의 실제 응답 필드·페이지 계약을 먼저 확인. 완전/부분/빈 결과·재시작 검증 | 자동 원장 정산·pending 해제·예약 재사용 |
| 다음 2: R2 실시간 수집 기반 | `feature/realtime-market-feed` | KIS 프로토콜·정규화 이벤트·재접속·분봉·저장·앱 구독 | M04 신청/권한·구독 상한 별도 확인. 재생 시험과 승인된 읽기 연결 결과 구분 | KB 스트리밍 추정·실시간 가격만으로 주문 활성화 |
| 다음 3: R3 증분 사건 수집 | `feature/research-event-sync` | 다중 페이지·체크포인트·중복/정정 처리·공개/수신 시각 | D01/D02 페이지·한도 검증, 기존 저장 자료 보존 | 검색 결과를 전체 원문으로 표시·무제한 호출 |
| 병행 준비: R5/R10 | 해당 기능별 브랜치 | 과거 자료 가용성·일별 자산/현금흐름 저장 설계 | 출처/활용 조건·숫자/시점 계약과 연결 | 누락 과거 성과 생성·수집만으로 모델 검증 완료 |
| 답변 후: R7/R8/R9 실제 확장 | 해결한 계약별 `feature/` 또는 버그별 `fix/` | 답변을 fixture로 고정하고 제한된 변경 구현 | 관련 KB-01~06 재개 조건·독립 검증·별도 승인된 실거래 | 미해결 항목을 묶어 일괄 활성화 |

다음 첫 구현은 **R1의 읽기 전용 계좌 스냅샷 계약**으로 잡습니다. 이번 R0 문서 작업에서 그 코드까지 구현된 것은 아닙니다. 계좌 관찰과 주문 종결의 쓰기 경로를 분리해 KB 답변 대기 때문에 데이터 수집·표시 개발이 중단되지 않게 합니다.

각 작업은 최신 `develop`에서 별도 분기하고 검증 후 PR로 통합합니다. 이 문서는 구분된 작업 목록이며 여러 브랜치/에이전트를 이미 동시에 실행하고 있다는 뜻은 아닙니다.
